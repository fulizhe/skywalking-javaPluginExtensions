# 指标分位「最差分钟」排障页（③ 语义）+ 服务端只读最差聚合

Status: ready-for-agent

## Problem Statement

开发者在大屏上看**范围 / 小时 / 表格**视图的分位时，聚合口径是"对每个桶的 p50..p99 做 `requestCount` 加权平均"（服务端 `TraceMetricsRollup.merge`、前端 `aggSeries`）。加权平均会把**局部尖峰平均掉**、系统性低估尾部——排障时最想发现的"某一分钟突然抖了一下"反而被抹平。

这是 Phase 5 的 **v1 已知偏差**（见 `h2-metrics` spec）。要拿到"真值"（把各桶原始样本汇到一起重算）必须上直方图/schema 变更（方案 ①），属另一条线。

但排障场景真正要回答的是**"这个范围内最坏的那一分钟有多坏、哪个端点最坏"**——这个问题用**现有的逐桶分位**就能回答，**不需要 schema 变更**。而目前没有任何视图回答它：`metrics.html` 只给加权平均，也没有"按最差排序的端点表"。

（背景与量化对比见 `docs/todos/h2化-phase5-metrics-端点基数治理方案.md` §5.1；③ 的取舍曾用一次性原型（单文件，已删除、不留档）验证。）

## Solution

新增一个**长期排障页**（独立页面，`metrics.html` 保持不动），以 ③ 语义展示分位：

- **全局视图**：把"当前·加权平均"与"③·最差分钟"并排，并给出**中位分钟**、**有数据桶数**与**每桶 P99 的小分布**——用分布而非单个数字，避免"最差"被断流小样本噪声带偏。
- **端点表**：每端点一行，**默认按"最差分钟 P99"降序**，一眼扫出最坏端点；同时保留现有"加权平均"作对照。
- **单端点下钻**：点端点 → 该端点逐桶 P99 曲线 + ③ 摘要（最差/中位/桶数/分布），并复用既有下钻入口（慢查询 / 双源对照 / 链路可视化）。

服务端**仅新增一个只读聚合字段**：`aggregate=true` 的每端点行追加各分位的**桶内最大值**与**桶数**（纯 SQL `MAX` + `COUNT(DISTINCT)`，**不改表结构、不改写路径**）。

## User Stories

1. 作为单体应用的开发者，我想一眼看到"当前这个时间范围内最坏的那一分钟，P99 有多坏"，以便判断是否存在被平均掉的抖动。
2. 作为单体应用的开发者，我想在同一张图上看到"加权平均 P99"和"最差分钟 P99"，以便直观看出两者差多少、当前口径是否掩盖了尖峰。
3. 作为单体应用的开发者，我想看到端点表**按最差分钟 P99 降序**，以便先排查最坏的接口，而不是按请求数排序。
4. 作为单体应用的开发者，我想在端点表里同时看到"最差分位"和"加权平均分位"两列，以便识别"平均值正常但偶发极差"的端点。
5. 作为单体应用的开发者，我想点开某个端点看到它的**逐桶 P99 曲线**，以便定位是哪一段时间在抖。
6. 作为单体应用的开发者，我想在下钻里看到该端点的**中位分钟**与**每桶分位分布**（而非单一最差值），以便区分"真实持续劣化"与"个别分钟噪声"。
7. 作为单体应用的开发者，我想看到每个端点**有数据的桶数**，以便知道"最差"是基于多少分钟算出来的、是否可忽略断流分钟。
8. 作为单体应用的开发者，我想下钻能直接跳到既有入口（慢查询 / 双源对照 / 链路可视化），以便从指标定位到现场链路。
9. 作为单体应用的开发者，我想这个页面在 `1h / 6h / 24h / 7d / 30d` 五档范围下都可用，以便从近到远排查。
10. 作为新读者，我想页面明确标注"本页分位 = 范围内最差分位，与 `metrics.html` 的加权平均口径不同"，以便不把两个页面当成同一口径。
11. 作为新读者，我想页面提示"断流 / 小样本桶会放大最差值"，以便不被单条样本误导。
12. 作为插件作者，我想服务端只做**只读取数**（`MAX` 分组），不改表结构、不改写路径、不改告警，以便零风险、零回归。
13. 作为插件作者，我想新字段是**向后兼容的追加**（老调用方不受影响），以便不破坏既有 `/inner/sw/metrics/query` 契约。
14. 作为插件作者，我想"最差"的定义在各分辨率下一致（分钟表取分钟桶的 `MAX`，小时表取小时桶的 `MAX`），以便口径统一可解释。
15. 作为插件作者，我想分位计算仍只在服务端有唯一实现（最差来自 SQL，客户端只渲染），以便可测面收敛。
16. 作为验证者，我想验证回路能断言"每端点 `worstP99 >= 该端点任一桶的 p99`、且 `bucketCount` 与逐桶行数一致"，以便确认只读聚合正确。
17. 作为验证者，我想验证回路能断言"排障页 HTTP 200"，以便确认页面可访问。
18. 作为维护者，我想"最差分钟分位"成为**领域术语**（写进 `CONTEXT.md`），以便与"加权平均分位""池化真值"区分，不退化成同义词。
19. 作为维护者，我想 `metrics.html` **零改动**（不在其中改图表或算法），排障页作为独立视角，以便现有用户与口径不受影响。
20. 作为维护者，我想本页明确**不解决**"加权平均失真本身"（真值需直方图/schema，方案 ①），以便边界清晰、不埋期待。
21. 作为维护者，我想 ③ 取舍的结论被记录在本 spec（原型本身一次性、已删除），以便后续追溯"为什么是 ③ + 独立页 + 下钻"。
22. 作为后续阶段作者，我想本页的"最差"口径在将来上直方图（方案 ①）后仍成立、且能新增"真值"列并列，以便平滑演进。

## Implementation Decisions

- **服务端只读聚合**：扩展 `aggregate=true` 的响应，每个端点行（含全局保留键 `"*"`）**追加**字段：
  - `worstP50` / `worstP90` / `worstP95` / `worstP99` = 该 endpoint 在查询范围内**各桶对应分位的最大值**（SQL `MAX(p50/p90/p95/p99)`）。
  - `bucketCount` = 该 endpoint 在范围内**有数据的桶数**（`COUNT(*)`，行即桶）。
  - 纯 SQL、**不改表结构、不改写路径、不改 rollup**；字段只追加、向后兼容。
- **"最差分钟"的定义**：范围内各桶该分位的最大值；分辨率随范围路由（分钟范围取分钟桶，`>24h` 取小时桶）——小时范围下语义为"最差小时"，页面文案需随分辨率措辞。
- **在飞分钟计入**：当前尚未翻转的内存分钟桶也被当作一个桶纳入 ③（其 `worst* = 自身分位`、`bucketCount = 1`，经 `MetricsRow.selfAsWorst()` 并入后再合并）——否则应用刚启动、H2 未落桶时"最差"为空。这是"最差 = 各桶最大值"的自然延伸，不是新口径。
- **中位分钟 / 分布**：服务端**不算** median（H2 SQL 不划算）；由**前端**用已取到的单端点逐桶序列计算（薄逻辑），仅在全局视图与下钻中展示。
- **页面（新）**：`dashboards/metrics-troubleshoot.html`，沿用现有 `dashboards/` 结构与 echarts 风格。
  - 全局视图：取 `endpoint=*` 逐桶序列（现有）+ `aggregate=true` 的 `"*"` 行的 `worst*`；并排图"加权平均 vs 最差"，附中位分钟 / 桶数 / 每桶 P99 分布。
  - 端点表：数据来自 `aggregate=true`（每端点一行）；默认按 `worstP99` 降序；列含 `worstP50/P95/P99` 与加权平均对照 + `bucketCount`。
  - 下钻：点端点 → 拉该端点逐桶序列（现有 `?endpoint=<ep>`）→ 逐桶 P99 曲线 + ③ 摘要（最差/中位/桶数/分布）+ 既有下钻入口（慢查询 / 双源对照 / 链路可视化）。
- **前端保持薄**：③ 的"最差"数一律来自服务端；前端只做"中位/分布/逐桶渲染"。
- **merge 透传**：`TraceMetricsRollup.merge` 合并时携带 `worst*`（取最大）与 `bucketCount`（求和）；**分位数口径不变**（p50..p99 仍按请求数加权平均），仅新增可选字段透传，使小时/聚合行的 worst 不丢。
- **`metrics.html` 保持不动**：不改其图表/算法/口径。入口只经 `dashboards/index.html` 挂链接（是否在 `metrics.html` 加一行链接**不在本 spec**，如需另行确认）。
- **领域术语**：新增"**最差分钟分位 (worst-minute percentile)**"，定义如上；与"加权平均分位""池化真值"并列（写进 `CONTEXT.md`）。
- **不新增配置开关**：沿用只读查询，不加新配置项（与"只留 `enabled` 一个开关"的既有原则一致）。

## Testing Decisions

- **只测外部行为**，不测实现细节（不锁 SQL 文本、不锁私有方法）。
- **主 seam（最高）= HTTP 读口 `/inner/sw/metrics/query`**：扩 `validate-h2.ps1` 的端到端断言——造数后：
  - `aggregate=true` 每行含 `worstP50/90/95/99` 与 `bucketCount` 字段；
  - 对某端点，`worstP99 >=` 该端点逐桶序列里 `p99` 的最大值（**用 `>=` 而非 `==`**：查询降采样时桶 `p99` 可能被平均，而 `worstP99` 是存储桶的真实最大，恒 `>=`）；`worstP99 >=` 其加权平均 `p99`；
  - 按端点断言 `bucketCount > 0` 与 `worstP99 >= p99`；
  - 全局行 `"*"` 同款字段存在。
  - 先例：`validate-h2.ps1` 已在断言 `/inner/sw/metrics/query` 的行与口径自洽。
- **单元 seam = 存储聚合查询**（in-memory H2）：断言 `MAX` 分组结果与桶数。先例：`H2TraceSegmentStorageMetricsTest`；相关：`TraceMetricsAggregatorTest`、`TraceMetricsRollupTest`。
- **页面**：静态 JS 无单测先例 → 由 e2e 脚本断言"排障页 HTTP 200 + 读口含新字段"；其余人工目测。不新建 JS 测试基建。

## Out of Scope

- **不修"加权平均失真"本身 / 不产出"池化真值"**：那需要直方图 + schema 变更（方案 ①），另一条线。
- **不改 `metrics.html`** 的图表与算法。
- **不改写路径、不改 `trace_metrics_minute/hour` 表结构、不加 TTL、不引入 `median` 的 SQL**。
- **不改告警**；rollup 的**分位口径不变**（p 值仍按请求数加权平均），仅新增的 `worst*`/`bucketCount` 可选字段透传（见 Implementation Decisions）。
- **不做跨重启持久化**（H2 file 模式）。
- **不在服务端计算中位分钟 / 分位分布**（留给前端）。

## Further Notes

- **三种分位口径并列**，切勿混用：
  1. **加权平均分位**（当前 / 小时 rollup）——`metrics.html` 所显示；
  2. **最差分钟分位**（本页 ③）——范围内各桶分位的最大值；
  3. **池化真值**（未来方案 ①）——合并样本后重算。
- 本页**不是修 bug**，而是提供一个**正确的排障语义**；加权平均仍保留在 `metrics.html`。
- **原型**：曾用一次性单文件原型对比"加权平均 / 最差 / 中位 / 分布"，结论 = 采用 ③ + 独立长期页 + 端点下钻；原型本身一次性、**已删除、不留档**（结论即本 spec）。
- **ADR**：与 `ADR-04`（H2 内存全量 trace 持久层）**不冲突**——本项只加只读查询、不碰表结构/写路径。
- **术语缺口信号**："最差分钟分位"不在 `CONTEXT.md`，本 feature 落地时补齐（issue 04）。
