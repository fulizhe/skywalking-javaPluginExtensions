本页存在的意义（为什么需要"最差分钟"口径）

看慢端点请优先用本页的「最差 P50」列（p50 是唯一没有样本下限的分位）： 低频慢端点每分钟样本天然凑不满 20，p90/p95/p99 会被置空； TopN 榜在按 P95 / 最差 P95 / P99 排序前会把该列为空的行整行剔掉， 于是"越慢越容易被剔除"。本页不剔——只把全局 * 行排除， null 只排到末尾，所以慢端点一定在表里。 用法：点「最差 P50」列头排序（默认是「按最差 P99 降序」，那一列对慢端点是空的）。 也可以留在 TopN 榜把排序依据切成「平均耗时降序」—— 那个依据来自计数、恒有值，所有端点都会出现。两页同源，都是 /inner/sw/metrics/query?aggregate=true。

先给结论：单分钟的 p50/p99 并不"失真"，只是"抽样近似"——而且样本几乎代表了全部请求；真正会引入系统性偏差的是"跨桶合并 / rollup"那条路，不是 5000 这个采样上限本身。

为什么单分钟分位基本可信：

  • 请求数 / 错误数 / 慢数 / 平均耗时 / 最大耗时：精确——每个请求都无条件累加，不经过抽样。
  • p50 / p90 / p95 / p99：来自等概率蓄水池（前 5000 条先塞满，之后按概率随机替换），一分钟内每条请求入池机会相同；N≈7000 时保留 5000 ≈ 71%，是无偏近似，误差很小。
  • sampleCount 恒为 5000 只是"触顶"，sampleOverflow 只是溢出体检计数——都不代表分位算错。

真正的系统性偏差在合并：小时 rollup、按端点聚合、以及查询降采样时，代码对每桶的 p50..p99 做 requestCount 加权平均（TraceMetricsRollup.merge / 前端 aggSeries）。分位数不可相加——加权平均会把局部尖峰"平均掉"，系统性低估尾部。

本页做什么：不去伪造"池化真值"（那需要直方图 + schema，属另一条线），而是用现有逐桶分位给出"最差分钟"口径：范围内各桶取最大，直接回答"最坏的那一分钟有多坏、哪个端点最坏"；并同时给出中位分钟与桶数，避免被断流 / 小样本桶放大误导。与 metrics.html（加权平均口径）并排对比。

三种口径：加权平均（metrics.html） / 最差分钟（本页） / 池化真值（未来方案，需直方图）。
