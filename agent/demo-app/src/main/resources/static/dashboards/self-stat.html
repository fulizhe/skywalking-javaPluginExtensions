口径说明（先看这一段再引用上面的数字）
数字口径
丢段总数 两个来源相加：采集入口丢（DataCarrier 缓冲区满，{@code produce()} 返回 false） 与存储队列丢（写队列 4096 满）。两者都是"宁丢不阻塞业务"设计下的正常取舍， 但丢了就是丢了，所以单点给一个总数。
ignored / skippedWhenDisabled 不是故障：前者是 agent 采样标记为 ignore 的段，后者是运行时开关 /toggle?enable=false 期间主动跳过的段。两者都是"按设计不采"。
单批消费耗时 DataCarrier 消费线程处理一批段（transform + 按 traceId 合入 + 指标聚合 + 影子 accept） 的墙钟耗时。它跑在插件自己的线程上，不在业务线程上；业务线程只做一次入队。 峰值是插件开销的上界证据。
积压 depth 已入队但尚未写进 H2 的段数 = 队列待处理 + 正在写。持续上涨说明存储侧跟不上采集速度； 顶到容量就开始丢段。
H2 约占用 （估算） 行数 × 单行成本的单行估算，不是 H2 自报的字节数：H2 2.x 没有内存读口 （INFORMATION_SCHEMA.SESSIONS 无 MEMORY_USED、 Session 无 getMemoryUsage，已在 2.1.212 / 2.3.232 上实测确认）。 单行成本取自 docs/notes/2026-09-27-h2-mem-capacity-estimate.md §7.3 的实测 ≈800 B/行（同实例两点差分，偏上估计）。要精确值只能带外 jmap -histo:live。 页内 JVM 堆 那一栏是精确值，两者不要混读。
环形占用率 / 覆盖轮次 写指针 currIndex 是只增不减的逻辑字节游标（不是行号、不是文件偏移）； 物理落点对它取模，所以"占用率"绕圈后封顶 100%。wrapCount = 已完整绕过的圈数。 写指针本身持久化在文件头 16B，重启后接着走。
过期读 expiredReadCount 读回 null 且原因是"已被环覆盖"。这是预期行为（环写满的正常结果）， 与"从未写入"（missReadCount 减去它）分开计数——后者往往意味着写指针或 fsync 出过问题。
重启即失 本页除写指针外全部是进程内计数，重启清零（与 H2 内存层同语义，ADR-04）。 唯一跨重启存在的是环形文件本身与它的游标。
