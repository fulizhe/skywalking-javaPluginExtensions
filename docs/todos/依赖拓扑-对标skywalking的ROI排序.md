# 依赖拓扑 / 指标大屏：对齐 SkyWalking 的可借鉴项（按 ROI 排序）

- **写于**：2026-10-01
- **背景**：本仓已有「Trace 指标大屏」与「依赖拓扑」两块对外页面，主要用途是**对外宣传 / 给领导汇报 / 争取资源**（对自用是次要收益）。因此判断标准是 **ROI**，不是"功能完整度"。
- **参照对象**：`https://demo.skywalking.apache.org/`（核实为 **SkyWalking Horizon UI**，即当前新一代 Vue 界面）
- **核实边界**：Horizon UI 的存在、官方组件图标位置（`skywalking-booster-ui` 的 102 张 `src/assets/img/technologies/*.png`）**已核实**；下面对 SkyWalking 其它功能面的描述**来自既有认知，未逐项核实**。

---

## 0. 结论（先看这里）

| 判定 | 条目 |
| --- | --- |
| ✅ **建议做**（低成本、直接服务汇报） | #1 演示模式 · #2 依赖清单（谁在调我）· #3 慢调用 TopN 榜 |
| ⏸ 观望（等汇报确有需要再做） | #4 依赖边耗时趋势（要落库）· #5 告警↔拓扑联动 · #6 实例/进程看板 |
| ❌ **明确不做**（得不偿失） | eBPF Profiling · Service Mesh 拓扑 · Browser Monitoring · 日志全文检索 · Event 分析 · 火焰图 · BanyanDB 存储换型 · OTel 上报（**已支持**，不必自建） |

**建议就做 #1，最多再加 #2。** 二者都不碰插件、不碰读口、不新增存储。

## ✅ 建议做

### #1 演示模式（Presenter Mode）—— 最高 ROI，先做这个

**问题**：给领导看的东西，现在一屏里有 8 条口径说明、页内 caveats 长段落、时间窗/视图/停止刷新等操作控件 —— 看着像**调试页**而不是成品。

**做法**（纯前端，半天）：

1. 工具栏加一个「演示模式」开关，切换时给 `<body>` 加一个 class：
   - 折叠 `.caveats`（口径说明默认收起，鼠标悬停才展开）
   - 隐藏时间窗 / 视图切换 / 停止刷新等**操作控件**
   - 图例常驻、字号放大一档
2. 顶部一行**结论卡**（自动从数据算，不手写）：
   - 依赖拓扑页：`依赖 N 类 · 累计调用 M 次 · 错误率 x%`（数据源已有：`/inner/sw/topology` 的 `dependencies` 与 `counters`）
   - 指标大屏：`QPS x · 错误率 y% · P95 z ms`（数据源已有：`/inner/sw/metrics/query`）
3. 「上一页 / 下一页」在 **指标大屏 ↔ 依赖拓扑 ↔ 告警面板** 之间切换（纯 `location` 跳转 + 一个共同的极简外壳）。

**完成判据**：按一次按钮，三张页面在全屏下无任何运维控件、口径可按需展开、结论数字与读口一致；截图即可直接进汇报材料。

**验收**：结论数字与 `/inner/sw/*` 读口逐项核对一致（不能出现"图上 3 个依赖、读口 5 个"）。

---

### #2 依赖清单视角（「谁在调我」）

**价值**：为资源申请提供论据，例如 *"本进程对外依赖 5 类，其中 Cache/MQ 是新引入的；DB 走的是进程内 H2（无外部依赖）"* —— 这是"要不要拆单体"的决策依据，也是汇报里最硬的一段。

**成本**：**几乎为零**。插件侧的进程累计表已有（`dependencies`：组件名 / 层 / 累计调用 / 累计错误 / 首末见时间 / 去重操作名），只差一个视图。

**做法**：拓扑页加一个「依赖清单」档（或独立小节），一张表：组件 / 层 / 累计调用 / 累计错误 / 首次出现 / 最近出现 / 出口操作名；可按累计调用排序，支持点击回到总览档。

**完成判据**：清单行数与读口 `dependencies` 长度一致；"首次出现"能区分"一直都有"与"压测才开始碰"。

---

### #3 慢调用 TopN 榜

**价值**：争取资源最硬的证据 —— *"哪个端点慢、慢到什么量级"*。现在是明细表，看不出排名。

**成本**：小（数据已在 `/inner/sw/trace-slow` 与指标读口里），只做排序 + 版式 + 前 N。

**完成判据**：Top 10 与明细表逐行对得上；同一端点在不同时间窗的排名变化能被看出来。

## ⏸ 观望（等确有汇报需求再做）

| # | 条目 | 成本 | 什么情况下才值得做 |
| --- | --- | --- | --- |
| 4 | **依赖边的耗时趋势（24h）** —— 让依赖拓扑从"当前快照"变成"有时间轴" | **高**：依赖边要落 H2（新增表 + rollup + 读口时间范围 + 保留期清理），是一条独立 feature | 汇报需要讲"依赖关系/耗时随时间的变化"，而不只是"现在是什么样" |

| 6 | **实例/进程（JVM）与依赖数并排** | 中 | 汇报对象开始关心资源水位（而不是"功能覆盖"） |

## ❌ 明确不做（对本仓定位得不偿失）

| SkyWalking 的功能 | 不做的理由 |
| --- | --- |
| eBPF Profiling / Kernel Profiling | 要 eBPF 与特权的 agent，与"OAP-less 单体"定位正交；演示性弱、解释成本高 |
| Service Mesh 拓扑 | 本仓不是网格，拓扑会退化成单节点 —— 正是我们刚在页面上消灭掉的那个形态 |
| Browser Monitoring | demo 没有前端埋点诉求；为一个不存在的场景引入采集链路 |
| 日志全文检索（Log 集成） | 插件已有应用日志数据流但没有检索场景；为它引入存储与索引，ROI 差 |
| Event 分析（OOM / GC 事件流） | 偏 JVM 调优，对外汇报无感；本仓已有 JVM 面板 |
| 火焰图（Pyroscope / profiling trace） | 需额外部署 + 采样配置，改动面大、收益窄 |
| BanyanDB / 存储层换型 | 与"单体内、内存优先"的决策相反（见 ADR-03 / ADR-04） |
| OTel 上报链路 | **已经支持**（无侵入接入），不必再自建一套 |

## 附：我们已具备的能力（对齐 SkyWalking 的哪些部件）

| 本仓有 | 对应 SkyWalking |
| --- | --- |
| 指标大屏 `metrics.html`（QPS / 错误率 / P50~P99 / 5 档时间范围） | Dashboard 的 Time Series（Global / Endpoint 作用域） |

| 慢查询页 / 链路视图 / Trace 查询 | Trace 分析三件套 |
| Profile 面板 | Profiling（只读，不含 eBPF） |
