## 前提与边界

- 单 JVM 是设计立场，不是临时限制。trace parity、告警、指标聚合、本地 profiling 全部限定在本 JVM 内。
- 不引入中心化转发、不引轻量聚合收集器（那是另一条产品路线，不在本仓库目标内）。
- 下列 P0/P1/P2 的每一项，都应在「不破坏单 JVM 自包含」的前提下落地。

## P1 — 把「半截功能」收口（从半成品到可用品）

| # | 缝 | 现状 | 扩展做法 | 状态 |
|---|---|---|---|---|
| P1-1 | 本地 Profiling 未闭环 | `SWLogfileReporterUtils.startProfile() / getProfileDatas()` 全是空桩；`consume` 里还有 `TODO 处理profile`；`profile-local.md` 规划了火焰图但快照只落内存 | 把 `startProfile` 接到 `LocalProfileTrigger.startProfileTask`，`getProfileDatas` 从 `ProfileSnapshotLocalSender` 读取，前端输出火焰图所需的分层聚合 JSON | ☐ |
| P1-2 | 对外查询门面脆弱 | 状态全靠 `LogfileReporterStatusExposeInterceptor` 等 4 个拦截器**反射**进 BootService；Toolkit `statisticStatus()` 返回空 Map | 抽一个统一的 `StatusFacade`（经 BootService 读快照），替代零散反射；Toolkit 作为唯一对外 API，规避「插件 ClassLoader 读不到真实配置」那类坑 | ☐ |

> 价值：消除反射脆弱性、补齐 Profiling 输出、让告警从「能用」到「可信」，是把现有资产变成真正可交付能力的收口动作。

## 非目标（明确排除，因单 JVM 立场）

- **多实例聚合 / 轻量中心转发**：`README-trace-alert.md` 自陈「不包含其他微服务实例的数据」，trace parity 也只在本 JVM。本仓库不破这个边界，跨实例归一属于另一条产品路线，不进入 TODO。

---

## 隐性风险（落地任何一项前先看）

- **背压风险（代码注释已自曝）**：`mergeLogIntoStatMap` 在 `consume` 线程里**同步**调 `afterTraceMerged` 做告警评估，注释写明「会卡 DataCarrier 的 consume 线程，造成背压」。`AsyncTraceAlertDispatcher` 只把网络通知异步了，评估本身仍同步——高流量下应先把这个改成入队异步评估（建议排在任何 P0/P1 告警增强之前）。
- **依赖回落脆弱**：见 `[已实现]hutool-json-依赖错位分析.md`，`hutool-core` 未 shade 进 jar，运行期依赖应用 classpath，宿主不带即崩。

---

## 建议执行顺序

1. 先排隐性风险（背压异步化、hutool 依赖收口）——不动功能，先稳地基。
2. 再 P0：补 DB / 线程池采集 + 饱和度进指标系统。
3. 再 P1 收口：Profiling 闭环 + 统一状态门面 + 告警基线/抑制。
4. P2 看场景：存储可插拔、指标维度增强，按需推进。
