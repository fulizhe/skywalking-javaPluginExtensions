# H2 化 Phase 5：端点基数（`MAX_ENDPOINTS_PER_BUCKET`）治理方案

> **文档定位**：针对 Trace 指标聚合中「端点基数上限」的**方案讨论稿**（未实现、未落代码），由一次 8 小时持续压测的内存分析暴露，待 §5 拍板。
>
> **相关**：问题来源与实测数据见 [`docs/notes/2026-09-25-trace-metrics-stress-memory-analysis.md`](../notes/2026-09-25-trace-metrics-stress-memory-analysis.md)（8h 压测内存分析）。
>
> **权威 spec**：`.scratch/h2-metrics/spec.md`。本方案落地后需回写其「实现决策 / 已知偏差」。

---

## 0. 触发

8h 持续压测（`scripts/stress.ps1 -Continuous`）后做内存分析，列出插件侧需盯的两个真实增长点，其一即「**端点基数 × 蓄水池**」：

> 真实应用 URL 带 path 变量时，端点会冲到 `MAX_ENDPOINTS_PER_BUCKET=500`（`endpointOverflow` 此时才开始计数）；则 `4×501×40KB≈80MB` 仅为样本数组，且分钟表行数 ×500。

本方案把该问题拆开、给出可选项与推荐路径。

## 1. 影响面：影响什么、不影响什么

- **全局保留键 `"*"` 独立累加、精确** → **全站请求数 / 错误率 / 分位永远准**，不因端点上限失真。
- 受影响的是 **per-endpoint 明细**：超过上限的端点并入 `(other)`，明细不可查。
- 结论：这是「**明细保真度 trade-off**」，不是 KPI 正确性问题。

## 2. 现状与两个子问题

代码锚点：`agent/logfile-reporter-plugin/src/main/java/org/apache/skywalking/apm/agent/core/reporter/logfile/metrics/TraceMetricsAggregator.java`
（`MAX_ENDPOINTS_PER_BUCKET=500`、`MAX_SAMPLES_PER_KEY=5000`、`Accumulator.samples = new long[5000]`、`accumulate()` 溢出逻辑、`flushClosedBuckets()`、`toHourRows()`）。

### 2.1 保真：是"先到先归并"，不是"top-N"

`accumulate()` 中一旦桶内端点满 500，**后到的新端点**一律进 `(other)`。后果：早期出现一次的冷端点占住名额，之后的高频热点反被并走 → 明细张冠李戴。

> spec 原文要求「按 request_count 归并（top-N）」，实现为"先到先"，已记为 v1 已知偏差。

### 2.2 规模：样本数组与 H2 行数才是大头

- **内存**：每 `Accumulator` 预分配 `long[5000]`＝**40KB** → 4 个桶 ×（500 端点 + `*` + `(other)`）× 40KB ≈ **最坏 80MB**。
- **H2**：分钟表 `2880 × 501 ≈ 144 万行`（48h）、小时表 `720 × 501 ≈ 36 万行`（30d）——在 H2 内存模式 + 索引下可能比 80MB 更贵。

> 真问题优先级：**2.2 规模 > 2.1 保真**（保真是"取哪 500 个"，规模才是内存/存储成本）。

## 3. 方案选项

### 轴 A — 保真（取哪 500 个）

| 选项 | 做法 | 收益 | 代价/风险 |
|---|---|---|---|
| A1 Top-N 最小堆 | 桶内按请求数维护最小堆，满员时新端点与堆顶比较，大则替换、被踢者并入 `(other)` | 精确保 top-N，O(log N) | 需维护堆与"被踢再出现"的语义 |
| A2 Space-Saving | 固定 K 计数器 + 误差上界，近似 heavy-hitter | 内存固定、实现成熟 | 计数为近似值（有误差上界） |
| A3 先到先 + 观察区 | 冷启动端点先只计数、达阈值才占名额 | 实现最简 | 仍非严格 top-N |

### 轴 B — 规模（内存）

| 选项 | 做法 | 收益 | 代价/风险 |
|---|---|---|---|
| B1 准入阈值 | 新端点在同桶内先只计数，达 K 次（如 ≥5）才分配样本，否则进 `(other)` | 长尾 singleton 不再分配 40KB | 需有界的 pending 计数结构 |
| B2 懒分配样本 | `long[]` 首次用到才 new | 对极短尾有效 | 对 500 热点无效 |
| B3 降样本上限 | `MAX_SAMPLES_PER_KEY` 5000→1024 | 40KB→8KB，最坏 80MB→16MB | p99 估计精度略降 |
| B4 v2 直方图 | `long[5000]` 换对数分桶（HdrHistogram/自研 `int[~200]`≈0.8KB） | 最坏 **80MB→~1.6MB**，与基数解耦 | 属 spec 预留的 v2 seam，表结构不变 |

### 轴 C — 源头降基数

| 选项 | 做法 | 收益 | 代价/风险 |
|---|---|---|---|
| C1 端点归一化 | 把 path 中**纯数字/UUID 段**折叠为 `{id}` | 从源头压缩基数 | 过猛会误并（`/order/abc` vs `/order/123`）；Spring MVC 的 `operationName` 已是映射模式，收益主要在未映射/通配/静态/探针路径 |

### 轴 D — 存储（H2 行数）

| 选项 | 做法 | 收益 | 代价/风险 |
|---|---|---|---|
| D1 只落 top-N | 长尾并成单条 `(other)` 落库 | 行数受 cap 约束 | 已近似此形状，只是"先到先" |
| D2 cap 可配/下调 | `MAX_ENDPOINTS_PER_BUCKET` 常量→配置，或默认降到 100–200 | H2 行数按比例降 | 明细变少；与 spec「常量防配置蔓延」冲突 |
| D3 长尾不落明细 | 长尾只计入 `*`，不落分钟明细 | 行数最少 | 口径需文档化 |

## 4. 推荐分阶段

> ⚠️ **本节为 2026-09-25 原始提案，已被 §5.1 的决定覆盖，勿直接照此排期。** 现状：B3 随 ⓵ 挂起、D2 随 ⓶ 拆分（A1 否 / B2 开放）、A1 与 B1 被 ⓷ 阻塞、**全部取决于 ⓪ 的测试环境实测**。以 §5.1 为准。

### v1.1（小改，先止血；集中在 `TraceMetricsAggregator` 一个类）

- **A1**（top-N 最小堆）修保真：热点不再被误并。
- **B1**（准入阈值）长尾不分配样本。
- **B3**（样本上限 5000→1024）削峰值。
- **D2**（cap 可配，默认降到 ~200）压 H2 行数。

单测可覆盖：热点不被误并、长尾不分配数组、溢出按请求数、cap 生效。

### v2（结构优化）

- **B4** 直方图替换 `long[]` → 内存与端点基数基本解耦，cap 可放宽到 1000+。
- H2 行数再单独决策（D1/D3）：是否只保 top-N、长尾是否落明细。

### 5.1 已产生的决定与挂起项（2026-09-26）

> 与 [实现细化](h2化-phase5-metrics实现细化.md) §16 的待办交叉核对后，逐条落定如下。**未列出者仍为 §5 待拍板。**

#### ⓪ 阻塞项：B4 直方图 —— 挂起，待测试环境实测

**决定**：⏸️ **本轮不实施**，先在测试环境量数据，量完再定。

**为什么挂起**（决策上下文，避免以后重新推导）：

| 维度 | 内容 |
| --- | --- |
| 它是什么 | 把 `Accumulator` 里"存 5000 个延迟样本"（`long[5000]` = 40KB）换成"存约 200 个对数桶"（`int[~200]` ≈ 0.8KB） |
| 唯一确定收益 | **内存省约 50 倍**：最坏 4 桶 × 502 组合 × 40KB ≈ 80MB → ≈ 1.6MB |
| 附带收益 | 不再丢样本 → `sample_count` 恒等于 `request_count`，尾分位从"无界采样误差"变成"有界分桶误差"（**不是变精确**，对数桶在 p99 附近分辨率低） |
| ❌ 修不了的 | "小时 rollup 加权平均近似"——`TraceMetricsRollup.java:142-145` 只有分钟行的 p50/p90/p95/p99，原始样本在分钟翻转时已丢；除非给分钟表加列，与 §3 B4 的"表结构不变"冲突 |
| **成立前提** | 80MB **只在端点打满 500 时才出现**。端点常态几十个 → 总占用约 3.5MB，改造即纯浪费 |
| 前置事实 | `TraceMetricsAggregator.java:366` 字段初始化即 `new long[MAX_SAMPLES_PER_KEY]`，不用也占 40KB（故 §3 B2 懒分配是现成可选项） |

**怎么测**（测试环境，一次即可）：

##### ⚠️ 先分清两个互不相干的阈值

初读本文最容易把它们混成一个。**B4 只对第二个有救**：

| | 阈值 | 作用域 | 触发后果 | 看哪个计数器 | B4 有用吗 |
| --- | --- | --- | --- | --- | --- |
| **抽样退化** | 单分钟 **5000** 条 | **单个「分钟桶 × 端点」** | 只有 p50/p90/p95/p99 变抽样；请求数/错误数/慢数/平均耗时/最大耗时**永远精确**（`add()` 里这些是无条件自增，见 `TraceMetricsAggregator.java:380-390`） | `counters.sampleOverflow` | 治"精度"，但精度本来就不差 |
| **端点溢出** | 单分钟 **500** 个 | **单个「分钟桶」内的不同 endpoint 数** | 多出的并入 `(other)`，明细不可查；内存累积到最坏 80MB | `counters.endpointOverflow` | **治"内存"，这才是主战场** |

##### ⚠️ 要看的是"最热的那一个端点"，不是系统总 QPS

`long[5000]` 是**每个 `Accumulator` 实例各有一份**，而一个实例 = 一个「分钟桶 × 端点」。**5000 的额度每分钟重置**——某端点这分钟爆了 10 万次，下一分钟又拿到全新 5000 格。

所以折算阈值 `5000 ÷ 60 = 83.3` **只对单个端点成立，对系统总 QPS 毫无意义**：

| 场景 | 单端点 QPS | 会不会抽样 |
| --- | --- | --- |
| 总 QPS 84，分散在 20 个端点 | ~4.2 | ❌ 差得远 |
| 总 QPS 84，全部打在一个端点 | 84 | ✅ 触发 |

**要问的问题只有一个：最热的那一个端点，一分钟多少请求？**

##### ⚠️ "单分钟计数" ≠ "长期平均 QPS"，突发同样触发

桶键是 `entry.getStartTime() / 60000`（自然分钟），落在该分钟内的请求全数计入，与到达时刻无关。因此：

```
某端点：10 秒内冲 5000 次，然后静默 50 秒
→ 那一个分钟桶里就是 5000 条 → 照样触发
```

**不需要"持续 83 QPS 跑满一分钟"**；一分钟内任意时刻冲进去就够了。反之，一个端点长期 80 QPS 平稳跑反而安全。

##### 测法与判据

1. 跑真实流量或压测，读 `/inner/sw/metrics`。
2. **测最热端点**（不用新工具）：把返回的 `buckets[]` 按 `requestCount` 降序，**第一条**就是当前最热端点的单分钟请求数，与 5000 比。
3. 同时看两个计数器：

   | 观测 | 结论 |
   | --- | --- |
   | `endpointOverflow` 持续 > 0 | 端点真会打满 → **做 B4**（并回头看 §5 第 2 问是否放宽 cap） |
   | `sampleOverflow` 持续 > 0 | 存在超 5000 的热端点 → B4 的精度收益也成立 |
   | **两个都长期 = 0** | **B4 对本系统没有任何价值，直接从待办划掉** |
   | 任一 > 0 但数值极小 | 记下量级再判——溢出 1~2 次和持续溢出不是一个问题 |

4. 若 `endpointOverflow` > 0，dump 被并入 `(other)` 的都是什么路径（404？探针？静态资源？），这直接决定 §5 第 6 问的 C1 归一化值不值得做。
5. 若要评估内存现状：`jmap -histo:live` 看 `long[5000]` 实例数与占用。

> **为什么值得先花一小时测**：B4 的两个收益各有前提（精度 → 要有单端点 >5000 的热端点；内存 → 要有打满 500 的高基数路径）。**两者都是"高负载/高基数"场景才成立的例外**，而 83.3 QPS 的单端点门槛在普通单体服务里并不常见。先量再写代码，可能直接省掉整个改造。

**连带影响**：§5 第 4 问（"先 B3 降样本数，还是直接上 B4 直方图"）被本项阻塞——见下条。

#### ⓵ B3 降样本上限（5000→1024）—— 不是独立项，是 ⓪ 的 else 分支

B3 与 B4 **互斥**：B4 若做，`long[]` 整个被替换，B3 就是"把一个即将被删的数组临时改小"——改完再删，白工一次，还多一次测试与发布。

**决定**：⏸️ **跟随 ⓪ 一同挂起**，不单独决策。

- 若 ⓪ 判定"做" → **B3 从 v1.1 删除**，直接上 B4。
- 若 ⓪ 判定"不做"（端点基数健康）→ B3 也**没有存在意义**（内存本来就不紧张）。**只有"将来发现端点确实会打满、但你就是不想上直方图"这个窄场景才需要 B3。**

#### ⓶ D2「`MAX_ENDPOINTS_PER_BUCKET` 可配」—— 拆分后只否掉一半

D2 原文把两件事捆在一起（`基数治理方案` §3 轴 D）：「常量→配置」**或**「默认降到 100–200」。这两件事性质完全不同，须分开判：

| | 提议 | 决定 |
| --- | --- | --- |
| **D2-a** | `MAX_ENDPOINTS_PER_BUCKET` 由常量改为**配置项** | ❌ **2026-09-26 定：不做。** 与已确认原则冲突——"只留 `enabled` 一个开关，其他写死防配置蔓延"（见 [实现细化](h2化-phase5-metrics实现细化.md) §12 决策 p）。这条原则当初就是为砍掉 `retention_days` 而立的，不宜转头又开后门 |
| **D2-b** | **默认下调**到 100–200 | ⏸️ 仍开放，但**优先级由 ⓪ 的实测结果决定**，且不受"防配置蔓延"约束（改常量即可） |

**D2-b 为什么不是"随便调"的旋钮**——这个数字与内存**线性绑定**：

```
502 个组合（500 端点 + "*" + "(other)"）× 40KB ≈ 20MB / 分钟桶
4 个桶 ≈ 80MB
```

调大不是免费：cap=1000 就是 160MB。**500 本质是"内存预算怎么分配"的决策，不是"一个参数"。**

**D2-b 的判据**（依赖 ⓪）：

- ⓪ 实测 `endpointOverflow` **长期 = 0** → **D2-b 也不做**。端点根本没打满 500，降 cap 只是**白白丢明细**，不省任何内存。
- ⓪ 实测 `endpointOverflow` **持续 > 0** → D2-b 与 B4 **二选一**：要么降 cap（省内存、丢明细，改动小），要么上 B4（省内存、**且不丢明细**，改动大）。此时按 ⓪ 的结论联动决定。

#### ⓷ A1（top-N 修保真）与 B1（准入阈值省内存）—— 被 ⓪ 的测量一并阻塞

**2026-09-26 决定**：

- **保真修法方向已定 = A1（top-N 最小堆）**，**A2（Space-Saving）、A3（先到先+观察区）关闭**——理由：既然已经溢出，就精确修，不再引入一个新的近似口径。
- **是否实施仍不单独决策**：A1、B1 与 B4 一样，取决于 ⓪ 的**同一个测量结果**（`endpointOverflow` 是否持续 > 0）。测出长期 = 0，则 A1 连同 §4 v1.1 一并不做。

**为什么**——它们都只在"端点打满 500"这个前提下才有意义：

| 观测 | A1（top-N 修保真） | B1（准入阈值省内存） |
| --- | --- | --- |
| `endpointOverflow` 长期 = 0 | **不需要**：从未发生"挤走谁"的问题 | **不需要**：内存本来就不紧张 |
| `endpointOverflow` 持续 > 0 | 有效：热点不再被冷端点挤走 | 有效：长尾不再各占 40KB |

**连带消解本文档的一处内部矛盾**：§2.2 断言"真问题优先级：**2.2 规模 > 2.1 保真**"，但 §4 v1.1 却把 A1（修保真）排在第一项。**在没有数据时这个排序无从判定**；一旦有了 `endpointOverflow` 的实测值，两个选项的收益可直接量化，矛盾自动消解，不必现在硬选。

**净效果**：⓪ 的那一次测试，**同时决定了 B3 / B4 / A1 / B1 / D2-b 五项的去留**。若两个计数器长期为 0，本文 §4 v1.1 与 v2 **整份作废**。

##### A1 一旦决定实施，实现要点（留给未来施工）

| 要点 | 内容 |
| --- | --- |
| 数据结构 | 桶内按 `request_count` 维护**最小堆**，堆顶 = 当前在册端点里请求数最少的那个 |
| 满员时 | 新端点与堆顶比请求数，**大则替换堆顶**，被踢者及其计数并入 `(other)` |
| **真正的难点** | **"被踢的端点又出现"要怎么处理**——它再次到达时是否重新参与竞争？这是 A1 唯一需要额外设计的语义，也是它比 A3 复杂的全部原因 |
| 与 B4 的联动 | 上了直方图（§4 v2）后内存不再是绑定，**cap 可放宽到 1000+ → 溢出减少 → A1 的紧迫性同步下降**。若 ⓪ 最终选 B4，A1 可考虑不做 |
| 单测 | ① 冷端点先到、热点后到，热点**不被挤走**；② 被踢端点再次出现的语义；③ `endpointOverflow` 计数与 `(other)` 行请求数守恒；④ 全局 `*` 行不受影响 |
