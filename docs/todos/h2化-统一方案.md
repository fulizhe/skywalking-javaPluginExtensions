## 1. 需求与目标

### 1.1 背景

`logfile-reporter-plugin` 是一个 **Agent 可选报告器插件**：把原本发往 OAP 的各类数据流拦截下来，改存进应用进程内的**有界本地缓存**，使单体能自查全链路与指标，无需 OAP。

当前短板：**所有本地数据都活在 JVM 进程内**。应用重启 / OOM / 容器销毁，链路数据全部丢失，故障现场无法复盘；且受内存与 FIFO 淘汰限制，**无法做历史回溯与审计**。

### 1.2 目标（本次迭代的真正动机）

1. **Trace 数据持久化**：引入[嵌入式 H2](https://github.com/apache/skywalking/blob/520d531fff8d2ba9687ff8b9086b7e27033a82bb/oap-server/server-storage-plugin/storage-jdbc-hikaricp-plugin/src/main/java/org/apache/skywalking/oap/server/storage/plugin/jdbc/h2/H2TableInstaller.java)，把 trace 从"进程内缓存"升级为"**可跨重启、可查询、可审计**"的本地历史数据 —— **对标 Glowroot** 的本地持久化体验。
2. **可审计**：Normal / Slow / Error 的判定结果**落库**，形成长期、可持续、可回溯的监控记录（当前只有**内存内实时告警**，见 [§2.4](#24-已存在的分级判定能力)）。
3. **基于 trace 的 metrics**：在 H2 历史数据之上沉淀 trace 维度的聚合指标（请求数、错误率、耗时、分位数），对标 Glowroot。

### 1.3 明确非目标（沿用三份草稿的共识）

- ❌ 不做 OAP Server、不引入 Elasticsearch / BanyanDB。
- ❌ 不做内置 HTTP Server（Spring Boot / Tomcat / Netty / REST）。
- ❌ 不复制 SkyWalking 做完整 APM。
- ❌ **不向 Business 暴露 Agent 自定义类型**（硬性 ClassLoader 约束）。
- ❌ **本阶段不做 log 持久化**（仅 trace；log 保留扩展位，见 [§4 Phase 6](#phase-6远期log-持久化--h2-内存模式统一扩展位)）。
- ❌ **不重复实现 SkyWalking 自带的 JVM / meter 指标持久化**（JVM 持久化已由 **RRD** 在外部完成，不在本插件范围）。
- ❌ 不在 Agent 内做可视化 / Dashboard / 图表。

### 1.4 本次迭代的边界（来自需求澄清）

| 维度 | 决策 |
| --- | --- |
| 第一阶段范围 | **只做 trace**；log 暂不做，但存储层要留扩展空间 |
| 分级持久化 | normal 只留最近窗口（半小时 or 2000 条，待评估）；slow 24h；error 7 天 |
| 表设计 | 参考 **SkyWalking OAP 9.4** 侧，**初期尽量少**（极简背景） |
| 写入模型 | 队列写入 + 异步消费 + 批量落盘（监控系统常规做法） |
| JVM 指标 | 已用 RRD 完成持久化，**不在本方案** |

## 2. 现状（以当前代码为准）

> 本节是三份草稿最需要纠正的部分。**所有结论均由代码核对得出。**

### 2.1 数据流全景

`CONTEXT.md` 定义插件接管**六类数据流**：链路段（trace segment）、JVM 指标、meter 指标、应用日志、心跳/实例信息、profile 快照。它们**不是同一条存储路径**：

```text
Agent 数据流                            存储形态（ADR-02）              载体
─────────────────────────────────────────────────────────────────────────
链路段 trace segment   ──►  键式（keyed，按 traceId 合并）  ──►  KeyedLocalStore
JVM 指标               ──┐
meter 指标             ──┤  追加式（append）              ──►  CircularBlockingQueue
应用日志 log           ──┤
profile 快照           ──┘
心跳/实例信息          ──►  另一路径（ServiceManagementLocalClient）
```

**关键纠正**：草稿 `h2化 -gpt.md` 把 `SWLogfileReporterUtils → LogReportServiceLocalClient → CircularBlockingQueue` 描述成"Trace/Log 的统一核心"——**错误**。那是 **log** 的路径；**trace 走的是完全独立的另一条路径**。

### 2.2 Trace 路径（本方案的主角）

**类**：`agent/logfile-reporter-plugin/.../agent/core/reporter/logfile/LogFileTraceSegmentServiceClient.java`

- 通过 `@OverrideImplementor(TraceSegmentServiceClient.class)` **替换** Agent 原生上报器（不是实现某个自定义 `Reporter` 接口——这是 `h2化-doubao.md` 的另一处错误）。
- 生命周期：`afterFinished(TraceSegment)` 投递 → `DataCarrier`（`CHANNEL_SIZE`/`BUFFER_SIZE`，`IF_POSSIBLE`）→ `consume(List<TraceSegment>)` **批量消费**。
- 转换：`SegmentObject` → `Log`（含 `List<SpanInfo>`，即 `spans`）→ `LogCollection.toMap()` → `Map<String,Object>`，**按 traceId 合并**存入 `KeyedLocalStore<String, Map<String,Object>>`。
- 内存中的最终结构：`Map<traceId, Map<"logs", List<LogMap>>>`（host JSON 契约 `data[traceId].logs`）。
- **已经具备队列 + 异步 + 批量消费的骨架**——H2 写入可直接复用这个批量窗口（见 [§6](#6-写入与读取模型)）。

**存储**：`KeyedLocalStore<K,V>`（包级可见，`final class`）

- 语义：`put` / `merge(key, fn) → V` / `snapshot() → Map` / `size()`；`LinkedHashMap` + 单 `ReentrantLock`；满则 **FIFO** 淘汰（非 LRU）。
- **注释明确写了与 `CircularBlockingQueue` "语义并行存在但不强行统一接口"**——与 ADR-02 完全一致。

**需再修正的一点（本方案新增）**：当前是在 `consume` 里按 traceId **就地强行合并成"整条链路"**。这是早期为降低实现难度做的权宜选择，实际运行中暴露出问题：存在不少**只有 grpc / hikaricp 的孤 segment**，按 traceId 归组后难以区分"这是完整链路，还是只有孤立的片段"。这与 OAP 的做法也不一致——**OAP 按 segment 逐条落库，查询时再按 traceId 组装**。

因此本方案把"合并/组装成整条链路"从客户端**下移进存储实现**：抽象边界前移到 `consume(List<TraceSegment>)` 的入参，`KeyedLocalStore` 及 traceId 合并降为内存实现的内部细节。迁移采取**只新增、并行双跑、验证后再切流移除旧逻辑**的**绞杀者**式两步走（详见 [§4 Phase 1](#phase-1trace-存储抽象只新增并行双跑)）。

### 2.3 已存在的分级判定能力

**包**：`agent/logfile-reporter-plugin/.../agent/core/reporter/logfile/alert/`

现状（`README-trace-alert.md`）：

- `TraceEvaluator` + `RulesEngine`：启动期编译规则，运行期只读匹配。
  - **ERROR 判定（L1/L2/L3）**：span `isError`、HTTP `status_code >= http_error_status_min`、SPI 自定义；可被 `error_ignore_rules` 白名单按 span 豁免。
  - **SLOW 判定**：`operation:` / `url:` 的 **Ant 路径**差异化阈值，否则 `default_slow_threshold_ms`。
- `AsyncTraceAlertDispatcher`：segment 合并后异步评估，命中则经 **HTTP webhook 或 SPI** 通知外部；同 traceId 去重（`NOTIFIED_CACHE_TTL_MS`）。
- `TraceAlertMetrics`：进程内累计计数（dispatch/http/rules hit），**在内存**。
- `AlertType` 枚举目前只有 `ERROR` / `SLOW`（**没有 NORMAL**）。

**关键纠正**：三份草稿都把"Normal/Slow/Error 分类"列为**未来 Phase 3 从零实现**。事实是：

> **判定逻辑（含阈值、白名单、规则引擎）已经完整存在，但用途是"内存内实时告警"。**
> 引入 H2 的目的**不是重新分类**，而是把**已有的判定结果持久化**，实现"长期、可持续、可审计"的监控 —— 对标 Glowroot。

因此 H2 阶段的正确做法是：**复用 `TraceEvaluator` 的判定结果**，只增加"写库时打 `trace_level` 标签 + 按级别分 TTL"，**不重造分类器**。

### 2.4 已存在的指标（澄清 metrics 的范围）

以下**都是 SkyWalking Agent 自带的指标**，插件只是把它们的输出本地化：

| 类 | 指标 | 现状 |
| --- | --- | --- |
| `JVMMetricsLocalSender` | JVM（CPU/内存/GC/线程/类加载） | 本地缓存；**持久化已由 RRD 在外部完成** |
| `MeterLocalSender` | meter 指标 | 本地缓存 |
| `TraceAlertMetrics` | 告警运行指标 | 进程内累计 （注意：这是自己做的，非skywalking） |
| `ProfileSnapshotLocalSender` | profile 快照 | 本地缓存 |

**关键澄清**：本方案要的 **metrics 不是上面这些**，而是**基于 trace 数据、沉淀到 H2 的聚合指标**（请求数 / 错误率 / 耗时 / p50-p99），对标 Glowroot。二者不可混为一谈：

- 现有 JVM/meter 指标 → SkyWalking 采集、本地快照、**RRD 已持久化**，**不属于本方案**。
- trace 聚合指标 → **本方案 Phase 5**，**只建立在 H2 历史数据之上**。

### 2.5 对外暴露机制

**入口**：宿主工具类 `SWLogfileReporterUtils`（桩在 `agent/demo-app/.../toolkit/`，运行期由 Agent 拦截）。

- 现有 API：`enableReport` / `disableReport` / `statisticStatus` / `startProfile` / `getProfileDatas`（草稿只提了前三个，遗漏了 profile 两个）。
- `statisticStatus()` 的实现：`LogfileReporterStatusExposeInterceptor` 拦截静态方法，**通过 `ServiceManager` + 反射**跨 `PluginClassLoader` 取数，拼成 `Map<String,Object>`：
  ```text
  data / jvm / instanceProperties / meterData / logData / profileSnapshotData / traceAlert
  ```
- **为什么用反射**：拦截器跑在 PluginClassLoader，直接引用 Agent 内部类会读到另一份副本（`README-trace-alert.md` 有明确警告）。**H2 阶段必须沿用这个范式**。

### 2.6 现状纠正表（对三份草稿的逐条纠错）

| # | 草稿说法 | 代码事实 | 纠正 |
| --- | --- | --- | --- |
| 1 | `LogReportServiceLocalClient` 统一管理 Trace+Log | 它只管 **log**；trace 在 `LogFileTraceSegmentServiceClient` | 双路径，见 §2.1 |
| 2 | Phase 1 在 `LogReportServiceLocalClient` 抽 `LogStorage{add,getAll}` 包 `CircularBlockingQueue` | 那是 **log/追加式** 路径；本阶段只做 trace | Phase 1 抽象**面向 segment 的 trace 存储**（入参 `List<TraceSegment>`） |
| 3 | Normal/Slow/Error 是未来 Phase 3 | 判定逻辑**已存在**，用途是内存实时告警 | H2 只做"落库打标 + 分 TTL" |
| 4 | Metrics 当前明确不做 | JVM/meter 是 SW 自带；要的是 **trace 聚合** | 范围切分为 §2.4 |
| 5 | doubao：实现 `Reporter` + `LocalTraceReporter` | 本项目用 `@OverrideImplementor` 替换 ServiceClient | 骨架不可照抄 |
| 6 | 旧文档称内存队列为 "LRU" | 实为 **FIFO**（ADR-02 已纠正） | 统一用 FIFO |
| 7 | doubao 的 H2 TTL SQL 用 `DATEADD('DAY',...)` | H2 不支持该 MySQL 语法 | 截止时间在 Java 侧算好，参数化传入 |
| 8 | 未提及 | 仓库有 stray 文件 `SWLogfileReporterUtils2222222222222.java` | 建议清理（见 §10） |

## 3. 核心约束（硬性）

1. **ClassLoader 边界**：Business ↔ Agent 只允许 JDK 原生类型（`Map` / `List` / `String` / `Long` / `Integer` / `Boolean` / `byte[]`）。Agent 内部模型不得出现在宿主工具类的签名中。
2. **不改宿主工具类 API**：`enableReport` / `disableReport` / `statisticStatus` / profile 两个方法的**调用方式与返回契约不变**。
3. **存储藏在 Agent 内部**：Business 永远不知道 H2 / JDBC / SQL / 表 / Repository / 事务。
4. **有界 + FIFO + 防御性快照**：延续 `CONTEXT.md`「有界数据存储」语义。
5. **尊重 ADR-02**：不强行统一两种存储形态。
6. **H2 后置**：先抽象 → 再 H2 → 再分级 → 再 Query → 最后 metrics。
7. **需求驱动抽象**：不提前设计几十个接口；不提前创建空层。
8. **极简 & 个人维护**：代码量 / Bug 数 / 维护成本是核心约束，优先级 = 简单 > 可维护 > 满足需求 > 扩展。
9. **参考 OAP 但不引入 OAP**：借鉴 OAP 链路表 `SegmentRecord`（表 `segment`）的字段语义与 `time_bucket` TTL 模式；**不依赖 OAP 存储类**、不嵌入 OAP Server。
10. **trace 写入口最终收敛到存储接口（两步走）**：Phase 1 先在 `consume` 里**只新增** `TraceSegmentStorage.accept(List<TraceSegment>)` 调用、新旧并行双跑，**既有逻辑零改动**；验证通过后再切流，把"合并/组装整条链路"下移进存储实现。告警的**判定逻辑不变，触发点随组装视图一起下移**（见 §6.3）。
11. **Metrics 只建立在 H2 之上**：内存模式不做指标聚合（进程内的 `TraceAlertMetrics` 运行计数不属于此处的 Metrics）。

## 4. 阶段路线（修订后）

```text
Phase 1  trace 存储抽象（只新增、并行双跑、零行为变化）
   ↓
Phase 2  H2 持久化（trace only，先内存模式打通，再切 file）
   ↓
Phase 3  trace 分级持久化（复用已有判定结果 + 分 TTL）
   ↓
Phase 4  Query（traceId / 时间范围 / error / slow / service / endpoint）
   ↓
Phase 5  trace-based Metrics（落 H2，对标 Glowroot）
   ↓
Phase 6  远期：log 持久化（扩展位）+ H2 内存模式统一
```

### Phase 1：trace 存储抽象（只新增，并行双跑）

**总策略：只新增、不改动既有逻辑；新旧并行双跑、交叉对比；验证通过后再逐步移除旧路径——无痛替换（绞杀者式演进）。**

> **纠正**：草稿让 Phase 1 抽象 **log** 侧 `CircularBlockingQueue`（选错对象）。本方案的抽象**前移到 `consume(List<TraceSegment>)` 的入参**——接收 Agent 采集到的原始 segment，"合并成整条链路"最终下移进存储实现。

**第一步只做"新增"**：在 `LogFileTraceSegmentServiceClient.consume(final List<TraceSegment> data)` 里**保留现有** `segmentToLog` / `mergeLogIntoStatMap` / `KeyedLocalStore` 逻辑**原样不动**，仅**新增**一次 `storage.accept(data)` 调用，使新旧两条路径在**运行时并行**：

```text
consume(List<TraceSegment> data)
   ├─ [既有·保留不动] segmentToLog → mergeLogIntoStatMap → KeyedLocalStore（按 traceId 合并）+ 告警分发
   └─ [新增·并行]     traceSegmentStorage.accept(data)   ← 只写入新存储，不影响旧路径
```

**接口草案（工作名 `TraceSegmentStorage`，命名见 §11）**：

```java
public interface TraceSegmentStorage {
    /**
     * 写入：与 consume 入参一致，接收 agent 采集到的原始 segment。
     *
     * 返回值【待定】：告警若整体下移（见 §6.3），本方法无需回传"受影响 trace 视图"，保持 void。
     * 具体形态待参考 SkyWalking OAP 的告警实现后再定（当前双跑期也不需要返回值）。
     */
    void accept(List<TraceSegment> segments);

    /** 读取：已组装 trace 快照（内存实现 = 与现有 data[traceId].logs 对齐，供交叉对比）。 */
    Map<String, Map<String, Object>> snapshot();

    int size();
}
```

**并行双跑的关键注意点**：

- **副作用唯一**：双跑期**告警分发仍只由旧路径驱动**（webhook/SPI 绝不能双发）；新路径 `accept` 只写自己的 store。
- **交叉对比**：用旧 `getLogfileStatMap()` 与新 `snapshot()` 逐 traceId 比对（trace 条数、logs 数、字段），差异须可解释才继续。可加临时 debug 打点（后续删除）。
- **零行为变化**：`enableReport` / `disableReport` / `statisticStatus()` 对外输出完全不变——因为读取仍走旧路径。
- **入参是 `TraceSegment`（Agent 内部类型）**：用于 Agent 内部的存储接口**不越 Business 边界**（那条硬约束只管宿主工具类）。
- **只做 trace**；4 个追加式 sender 及其 `CircularBlockingQueue` 一律不动（ADR-02）。

**验收标准（关键）**：
- **旧逻辑零改动、零行为变化**：`statisticStatus()` 的 `data[traceId].logs` 与改造前逐字段一致；告警行为与去重不变。
- 新旧数据**交叉对比一致**（或差异有明确解释并记录）。
- 验证回路（ADR-01：`validate.ps1`）全绿。
- **独立提交**：`feat: add parallel trace-segment storage sink (shadow run)`。**本步不引入 H2、不删旧逻辑。**

**后续（切流，分小步，不在本步）**：
- **Phase 1b（切流）**：旧路径验证通过后，分几次小改移除 `consume` 内的 `segmentToLog` / `mergeLogIntoStatMap`，"整条链路合并"完全下移进 `MemoryTraceSegmentStorage`；**告警触发点也随组装视图一起下移**——推荐用"纯存储 + `AlertingTraceSegmentStorage` 装饰器"承载（判定逻辑 `TraceEvaluator`/`AsyncTraceAlertDispatcher` 不变），客户端 `consume` 变薄为 `ingest(data)`；详见 §6.3。
- 每步可独立回滚，实现"**底层更换无感**"。

### Phase 2：H2 持久化（trace only，先内存模式后 file）

**引入顺序：先 **H2 内存模式**（`jdbc:h2:mem`）打通"写入 → 读取 → 查询/分级/TTL"整条链路，再切 **file 模式**（`jdbc:h2:file`）——小步快跑。**

- 新增 `H2TraceSegmentStorage` 实现同一接口，**JDBC 模式（mem/file）作为配置**，切换只改配置、不改代码；两种模式共享**同一份 schema/SQL/逻辑**。
- **Phase 2a（H2 内存模式）**：打通 Schema、JDBC、写入、读取、查询、分级、TTL 全链路，并与 `MemoryTraceSegmentStorage` 做双跑交叉对比。内存模式无磁盘副作用，最适合快速迭代。
- **Phase 2b（H2 file 模式）**：仅切换连接为 file，重点验证**磁盘相关风险**——文件锁、`kill -9`/断电损坏、MVStore 崩溃恢复、磁盘增长、跨进程占用。这些风险被**有意推迟到本步**（内存模式天然没有）。
- 表设计参考 OAP 链路表 `SegmentRecord`（表 `segment`，见 [§5](#5-h2-表设计参考-oap95极简)）。
- **因为抽象已前移到 segment 层，H2 实现可自由选择落库粒度**：天然支持"**一条 segment 一行**"（OAP 语义），也支持查询期再按 traceId 组装；不再被"写入前必须先合并整条链路"绑死。
- 写入模型：队列 + 异步 + 批量（见 [§6](#6-写入与读取模型)）。
- **注意区分**：H2 内存模式 ≠ Phase 1 的纯 Java `MemoryTraceSegmentStorage`。前者是用来验证 H2 代码路径的临时形态，后者是长期保留的进程内近期缓存。
- **Phase 1 的 memory 实现保留**（近期数据 / 低开销），H2 承担历史数据：
  ```text
  TraceSegmentStorage
     ├── MemoryTraceSegmentStorage   （纯 Java，进程内近期缓存；内部仍按 traceId 组装）
     └── H2TraceSegmentStorage       （先 mem 后 file；可配置模式；可按 segment 落库）
  ```

### Phase 3：trace 分级持久化

> **前提更正**：判定**已经存在**（`TraceEvaluator` + `RulesEngine` + `AlertType`）。本阶段**不重造分类器**，只做两件事：

1. **落库打标**：把 `TraceEvaluator.evaluate` 的结果（ERROR / SLOW / 默认 NORMAL）写入 H2 的 `trace_level` 列。判定口径与现有告警**完全一致**（同一套规则、同一套阈值、同一套白名单）。
2. **按级别分 TTL**（初值，待运行数据评估）：

   | trace_level | 保留策略（初值） | 说明 |
   | --- | --- | --- |
   | `error` | **7 天** | 最长保留，优先保全故障现场 |
   | `slow` | **24 小时** | 中期保留 |
   | `normal` | **最近半小时**，或**容量 2000 条**（二选一，待评估） | 短窗口；也可考虑不落库、仅留在内存 |

   **开放决策**：normal 用"时间窗口"还是"容量上限"，取决于实际 trace 量与磁盘增长，落地前用实跑数据定（见 [§11](#11-开放决策待评估)）。

- 优先级顺序沿用现有语义：`ERROR > SLOW > NORMAL`（`AlertType` 需扩展 `NORMAL` 或由"未命中即 normal"推导）。

### Phase 4：Query

按需求出现顺序逐步加，**需要什么加什么**：

```text
traceId  →  时间范围  →  error / slow（trace_level）  →  service / endpoint  →  更多条件
```

初期可以直接走 SQL（H2 已建索引），**不自研内存索引**。

### Phase 5：trace-based Metrics

- **只建立在 H2 历史数据之上**（不基于内存缓存）。
- 对标 Glowroot：请求数、错误数、错误率、平均耗时、p50/p90/p95/p99、endpoint 维度统计。
- 新增独立工具类（命名候选 `SWMetricsUtils` / `SWLocalMetricsUtils`），**与 `SWLogfileReporterUtils` 同范式**：
  ```java
  public static Map<String, Object> statisticMetrics()
  public static Map<String, Object> queryMetrics(Map<String, Object> condition)
  ```
- **只提供标准化 `Map` 数据，不做 UI**。外部消费者自行决定 Console / Web / IDE / Grafana / AI 消费。
- 聚合计算放在 H2 / Metrics Service，工具类只做 Facade，不承担 SQL/Aggregation 主体逻辑。
- 预聚合表（`trace_metrics_minute`）避免每次扫描全量明细，见 §5.3。

### Phase 6（远期）：log 持久化 + H2 内存模式统一（扩展位）

- **log 持久化**：本阶段不做。Phase 1 的存储抽象**不覆盖 log**（遵守 ADR-02），但接口/包结构预留扩展位，未来 log 若要持久化可平行增加。
- **H2 内存模式统一**（长期备选）：H2 支持 `File Mode` 与 `In-Memory Mode`，远期可能用 H2 内存模式替代独立的 `MemoryTraceSegmentStorage`，只维护一套实现。**现在不做**——需长期运行观察后再评估，且改动会触及 ADR-02 的边界，须新写 ADR。
- **采样策略**：高并发下按采样率降低存储压力（对齐 `afterFinished` 投递点）。
- **Trace 快照 Dump**：OOM 预警 / 内存满时导出链路 JSON，保存故障现场。

## 5. H2 表设计（参考 OAP 9.4，极简）

### 5.1 参考来源与适配说明

> **已按源码核实**（commit `520d531`），完整整理见 [reference/skywalking-oap-trace-storage.md](../reference/skywalking-oap-trace-storage.md)。

- OAP **没有 `.sql` 建表文件**；表结构由**代码里的 Model 类 + 注解**（`@Stream`/`@Column`/…）定义，`ModelInstaller`（H2 用 `H2TableInstaller`）**启动期运行时生成 DDL**。
- 链路表 = **`SegmentRecord`**，表名 **`segment`**（`INDEX_NAME="segment"`），附加表 `segment_tag`。**不存在 `skywalking_segment` / `skywalking_segment_ref`**（草稿说法有误）。
- 字段：`segment_id(150)` / `trace_id(150)` / `service_id(String)` / `service_instance_id(512)` / `endpoint_id(512)` / `start_time(BIGINT)` / `latency(INT)` / `is_error(INT)` / `data_binary(byte[], storageOnly)` / `tags` / `time_bucket`（基类 `Record`）。
- `service_id` / `service_instance_id` / `endpoint_id` **都是字符串**——本项目用字符串**并不偏离 OAP**（**更正此前"OAP 用整数 ID、依赖 service_inventory"的说法**）。
- **span 不单独成行**：整段 segment（含 spans）序列化进 `data_binary`；H2 类型为 **`MEDIUMTEXT`**（`byte[] → MEDIUMTEXT`），**不是 BLOB**。
- **载荷格式**：OAP 用 protobuf 序列化 segment；本项目**复用现有 `Log.toMap()` JSON** 写入 `data_binary`，不引入 OAP entity / protobuf（避免包膨胀与 shade）。
- H2 下 OAP **不建索引**（演示级）；本项目要查询性能需**自行建索引**。

**参考源码（一手，SkyWalking OAP @ 520d531）**：

### 5.2 明细表（Phase 2 最小表）

```sql
-- 一条 TraceSegment 一行；整段（含 spans）序列化进 data_binary（对齐 OAP SegmentRecord 的 data_binary）
-- 表名：对齐 OAP 可用 segment；避免与业务同库冲突可用 trace_segment。**不再用 skywalking_segment**（OAP 实际表名为 segment）
CREATE TABLE IF NOT EXISTS trace_segment (
    id               BIGINT AUTO_INCREMENT PRIMARY KEY,
    trace_id         VARCHAR(128) NOT NULL,
    segment_id       VARCHAR(128) NOT NULL,
    service          VARCHAR(256),
    service_instance VARCHAR(256),
    endpoint         VARCHAR(512),
    start_time       BIGINT  NOT NULL,   -- 毫秒时间戳
    end_time         BIGINT  NOT NULL,
    latency          INT     NOT NULL,   -- 毫秒
    is_error         BOOLEAN NOT NULL,
    trace_level      VARCHAR(16),        -- normal / slow / error（Phase 3）
    data_binary      MEDIUMTEXT,         -- Log/LogCollection 的 JSON 载荷（复用 Log.toMap）；OAP byte[]→H2 即 MEDIUMTEXT
    time_bucket      BIGINT  NOT NULL,   -- OAP 风格时间桶，供 TTL（如整分钟/整小时）
    create_at        TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE INDEX IF NOT EXISTS idx_trace_segment_trace_id    ON trace_segment(trace_id);
CREATE INDEX IF NOT EXISTS idx_trace_segment_time_bucket ON trace_segment(time_bucket);
CREATE INDEX IF NOT EXISTS idx_trace_segment_is_error    ON trace_segment(is_error);
CREATE INDEX IF NOT EXISTS idx_trace_segment_level       ON trace_segment(trace_level);
```

**二进制载荷列 vs 拆行 的取舍（记录以备复盘）**：
- 本方案 Phase 2 选 **单列载荷**（对齐 OAP `data_binary`）：表少、写入简单、适配"以 traceId 查整条链路"的主场景。
- 代价：**无法用 SQL 直接按 span 字段（接口名/异常/耗时）筛选**，需读载荷反序列化后在代码里过滤。
- 若未来核心场景变成"**按时间段/接口名/异常/慢请求大范围检索 span**"，再新增拆行表 `span_info`（物理结构与 OAP 不同），届时新写 ADR。

### 5.3 聚合表（Phase 5，后置）

```sql
-- trace 维度的分钟级预聚合（对标 Glowroot），避免每次查询扫描全量明细
CREATE TABLE IF NOT EXISTS trace_metrics_minute (
    id            BIGINT AUTO_INCREMENT PRIMARY KEY,
    service       VARCHAR(256) NOT NULL,
    endpoint      VARCHAR(512) NOT NULL,
    time_bucket   BIGINT NOT NULL,       -- 整分钟
    request_count BIGINT NOT NULL,
    error_count   BIGINT NOT NULL,
    slow_count    BIGINT NOT NULL,
    total_latency BIGINT NOT NULL,
    max_latency   INT,
    p50           INT,
    p90           INT,
    p95           INT,
    p99           INT,
    create_at     TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_metrics_service_endpoint_bucket
    ON trace_metrics_minute(service, endpoint, time_bucket);
```

### 5.4 TTL / Retention

**纠正**：草稿用 `DATEADD('DAY', -1, NOW())`（MySQL 语法），**H2 不支持**。截止时间在 **Java 侧**算好传入：

```sql
DELETE FROM trace_segment WHERE trace_level = 'normal' AND start_time < ?;  -- now - 30min（或按容量）
DELETE FROM trace_segment WHERE trace_level = 'slow'   AND start_time < ?;  -- now - 24h
DELETE FROM trace_segment WHERE trace_level = 'error'  AND start_time < ?;  -- now - 7d
DELETE FROM trace_metrics_minute WHERE time_bucket < ?;                     -- now - 30d
```

由 Agent 内部定时任务周期性执行（时间桶/水位线方式）。OAP 侧机制（已核实，`DataTTLKeeperTimer.java`）：单线程定时器按 `dataKeeperExecutePeriod` 分钟调度；**仅集群首节点执行**；遍历所有 model，按 `time_bucket` 调 `IHistoryDeleteDAO.deleteHistory(model, time_bucket, ttl)`，`ttl` 取 **record / metrics 两档全局值**——**OAP 不按 trace 级别区分**。

> 本项目按 `trace_level` 分级 TTL（error 7d / slow 24h / normal 窗口）是**有意的增强/偏离**；骨架借鉴"定时器 + `time_bucket` 水位线"，删除条件改用 `trace_level`。参考：<https://github.com/apache/skywalking/blob/520d531fff8d2ba9687ff8b9086b7e27033a82bb/oap-server/server-core/src/main/java/org/apache/skywalking/oap/server/core/storage/ttl/DataTTLKeeperTimer.java>。具体 TTL 值按实跑数据定，**不预设标准答案**。

### 5.5 依赖与打包

- **H2 版本锁定**：与 SkyWalking OAP 9.4 配套的 H2 版本保持一致（否则 H2 文件不兼容）。
- **依赖冲突**：插件内置 H2，若业务应用自带 H2 可能版本冲突 → **maven shade 重命名隔离**。
- **不依赖 OAP 存储类**：只抄表定义与转换逻辑；Agent 侧不能 `import` OAP 存储类。
- **先内存后 file（小步快跑）**：实现先用 `jdbc:h2:mem:<name>;DB_CLOSE_DELAY=-1`（`DB_CLOSE_DELAY=-1` 保证连接关闭后内存库不丢）打通链路，再切 `jdbc:h2:file:<path>`；**切模式只改配置**，代码与 schema 不变。
- H2 文件位置、缓存上限、MVStore 引擎、定时快照备份：落地时按需配置。

## 6. 写入与读取模型

### 6.1 写入：队列 + 异步 + 批量

写入统一入口是 **`TraceSegmentStorage.accept(List<TraceSegment>)`**（与 `consume` 入参一致）。trace 路径**已有** `DataCarrier` 批量消费骨架（`consume(List<TraceSegment>)`）。H2 写入有两种挂接方式：

- **方案 A：复用现有 `consume` 批量窗口**——最省事，但 DB I/O 会占满 DataCarrier 消费线程，可能反压采集。
- **方案 B（推荐）：`accept` 内转交独立的有界写入队列 + 专用写线程**——`accept` 只入队并完成内存组装/告警回传，单写线程按容量/时间触发 `JDBC addBatch/executeBatch`。与现有 `AsyncTraceAlertDispatcher` 的异步模式一致，**不阻塞业务线程、不阻塞 DataCarrier**。

约束：
- **禁止单条同步写磁盘/DB**（业务线程零阻塞）。
- 队列满策略：丢弃 + 计数打点（可配采样）。
- 批量大小参考 Agent 原生批量策略。

### 6.2 读取：内存优先，历史走 H2

- 近期数据：`MemoryTraceSegmentStorage.snapshot()`（现有 `data[traceId].logs` 契约不变）。
- 历史查询：H2（Phase 4）按索引查询。
- 热数据可内存缓存，老数据走 H2；查询性能相比纯内存下降可接受（内部自用）。

### 6.3 与告警的关系

`AsyncTraceAlertDispatcher` **继续负责实时告警**（webhook/SPI，不阻塞），`TraceEvaluator` 判定逻辑**不变**。**触发点随"组装视图"移动**：

- **双跑期**：告警只由**旧路径**驱动（旧 `consume` 逻辑原样），新存储 `accept` 不触发告警——**防新旧双发**。
- **切流后**：合并/组装下移进存储，组装视图由存储产出，**告警触发点随之下移**（不再由客户端编排）。推荐落点：**纯存储 + `AlertingTraceSegmentStorage` 装饰器**（`accept` 委托存储 → 对本批受影响 trace 逐个 `afterTraceMerged`）。存储保持纯粹可替换，告警触发只在装饰器写一次，不会在内存/H2 实现里重复。

> **告警实现待参考 SkyWalking OAP**：告警的判定/触发/通知如何组织，**待参考 SkyWalking OAP 的告警（alarm）实现**后再定（见 [§11](#11-开放决策待评估) #13）。注意：OAP 告警疑为**指标驱动**，与本项目 trace 级慢/错告警**可能不同构**——此为**待核实假设，勿当结论**。

H2 落库是**另一条并行链路**，复用**同一个** `TraceEvaluator` 判定结果，避免两套口径。

### 7.1 沿用宿主工具类范式（无 HTTP）

```text
Business / External Consumer
        │  JDK Native Types (Map/List/String/Long)

                                   └── AI 分析
```

## 8. ClassLoader 与打包风险（重点）

- 风险：自建 trace/span 自定义 POJO 由 Agent ClassLoader 加载，业务代码拿到会 `ClassCastException` / `LinkageError`。
- 规避：
  1. 对外**只用 JDK 原生类型**（`Map`/`List`/...）。
  2. Agent 内部模型（`Log`/`SpanInfo`/`KeyedLocalStore`/`TraceSegment`/H2 实体）**不跨越 Business 边界**（storage 接口入参 `TraceSegment` 仅限 Agent 内部使用）。
  3. 工具类编译期依赖桩类，运行期由 Agent 拦截器接管（对齐 `TraceContext` 模式）。
  4. **切勿把插件类定义在 `org.apache.skywalking.apm.agent.core.XXX` 目录下**（stray 文件 `SWLogfileReporterUtils2222222222222.java` 的注释即记录了该踩坑）。
  5. H2 通过 **shade 重命名**隔离，避免与业务应用冲突。

## 9. 风险清单（Wiki 归档）

| 风险 | 等级 | 缓解 |
| --- | --- | --- |
| H2 进程被 `kill -9` / 断电导致文件损坏 | 中 | 使用 MVStore；定时 H2 文件快照备份 |
| 高并发 span 写入导致磁盘 IO 高 | 中 | 异步批量写入 + 采样策略 |
| H2 依赖与业务应用包冲突 | 中 | shade 重命名隔离 |
| 内存队列打满丢 trace | 低 | 队列容量配置 + 采样 + 丢弃计数打点 |
| 数据无限膨胀 | 中 | 定时 TTL + 分级 TTL + 保留窗口 |
| 单列载荷方案无法 SQL 索引 span 内部字段 | 中 | 评估查询场景；需要时改拆行表（新写 ADR） |
| H2 版本与 OAP 不一致导致文件打不开 | 中 | H2 版本锁定，与 OAP 9.4 配套版本一致 |
| 直接引入 OAP 实体导致依赖膨胀/类冲突 | 中 | 只抄表定义与转换逻辑，不依赖 OAP；必要 shade |
| 自定义 trace POJO 跨类加载器导致 ClassCast | 高 | 不新增跨界 DTO；对外只返回 JDK 原生 Map |
| 两套存储（memory + H2）长期维护重复代码 | 低 | 远期可用 H2 内存模式统一（须新写 ADR） |
| 工具类静态方法在多类加载器场景下替换失效 | 中 | 遵循 TraceContext 宿主类模式，Agent 字节码拦截接管 |
| 分级判定出现两套口径（告警 vs 落库） | 中 | 强制复用同一 `TraceEvaluator` 结果，不重造 |
