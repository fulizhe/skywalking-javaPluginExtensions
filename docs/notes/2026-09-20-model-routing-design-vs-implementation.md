# 2026-09-20: 模型路由经验——设计讨论与代码实现的国内模型选型

> 范围：OpenCode/OMO 的模型选型策略（.omo agents/categories 路由）。状态：经验结论，非规范；**模型版本演进快，本文有时效性**。

## 背景

h2-trace-storage Phase 1 开工前讨论：设计讨论与代码实现分别该用什么国内模型。当时的可用池：Kimi-K3、Qwen3.7-Plus(1M)、GLM-5.2、MiniMax-M3、deepseek-v4-flash。

## 核心经验：按"容错方向"选模型，而不是按 IQ

| 场景 | 胜负手 | 推荐 |
|---|---|---|
| 设计讨论（grilling / to-spec / 架构咨询） | 深度推理、敢反驳不讨好、装得下全套文档的长上下文、中文结构化表达 | 旗舰推理档：Kimi-K3 或 DeepSeek 推理档 |
| 大范围读码 / 探索 | 上下文容量 | 长上下文档：Qwen3.7-Plus(1M) |
| 代码实现 / 执行票 | **工具调用稳定性**（连续几十次 edit/bash 不脱轨）> 单次 IQ | 主力：GLM-5.2 / Kimi-K3；MiniMax-M3 做对照 |
| 杂活（改错字、单文件小任务） | 便宜 + 快 | flash 档：deepseek-v4-flash |

三条原则：

1. **容错不对称**：设计的产出会外置成文档，幻觉在 grilling / 评审里会被抓（容错高，可以全力冲）；实现的产出直接进代码（容错低，"稳"比"聪明"重要——主力别用 flash 档）。
2. **成本结构不同**：设计 = 轮次少 × 单次大（可全用旗舰）；实现 = 轮次多 × 单次小（要分层：主力 + flash 混合，subagent 后台按 category 走便宜模型）。
3. **别信跑分，信自己的票**：拿一张真实票（如票 02 存储实现）让候选模型各做一遍，比三样——**一次通过率、工具调用脱轨次数、diff 质量**。一场实验胜过十篇评测。

## 展开：为什么"实现主力别用 flash 档"

flash 档 = 各家模型的轻量快速小杯（如 `deepseek-v4-flash`）：更小、更快、更便宜，为高并发、低价值密度任务设计。"实现主力"指执行实现票的主 agent。三个不对称：

1. **实现是一条长工具链**：一张实现票 = 连续几十次"读文件 → 改代码 → 跑测试 → 修"，每步依赖前一步正确。flash 档在长链路后段更容易忘掉前面的约束、漏边界条件、指令漂移、工具调用出错——旗舰与 flash 的差距主要显现在链路**后段**。
2. **容错不对称**：flash 省的是 token 钱（小钱）；实现产物直接进代码，写错付出的是 debug 时间 + 整票返工 + review 垃圾 diff（大钱）。设计写错只是改文档，被 grilling 抓住就完了。
3. **重跑成本倒挂**：杂活失败重跑几乎免费；实现票失败重跑是整张票的上下文与时间。期望成本算下来旗舰反而便宜。

对照：

| 任务 | 用什么 |
|---|---|
| 实现票（多步骤、要过验收） | 旗舰主力（GLM-5.2 / Kimi-K3） |
| 改错字、格式化、单个函数小改、总结一段话 | flash（验证成本低，重跑免费） |

一句话：**flash 适合"失败无所谓"的活，实现主力是"失败很贵"的活**。

## 当时结论（2026-09-20 落到 .omo 的路由）

- 推理 / 评审 / 规划（sisyphus、oracle、metis、momus、ultrabrain）→ Kimi-K3
- 读码 / 探索 / 深度分析（explore、librarian、deep）→ Qwen3.7-Plus(1M)
- 杂活 / 低强度（quick、unspecified-low）→ deepseek-v4-flash
- 待实证：实现类 category 用 GLM-5.2 与 Kimi-K3 各跑一票对比后定主力

## 时效性与复核

- 各家版本迭代快（本文写作时 K3 / Qwen3.7-Plus / GLM-5.2 均无可靠公开基准），结论有效期自检：换大版本时重跑一次票 02 样本即可。
- 复核成本刻意压低：验证回路（ADR-01）一条命令出结果，A/B 的判定锚点是"验证回路是否全绿 + diff 复读"。
