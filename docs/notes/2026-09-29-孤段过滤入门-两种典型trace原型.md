# 孤段过滤入门：为什么会有"孤段"，两种典型 trace 原型（小白向）

> **面向**：监控 / SkyWalking 新手。看完要能回答两个问题：这条 trace 是什么？插件会不会把它过滤掉？
> **配套**：底层 refs 口径见 `docs/reference/skywalking-trace-refs.md`；判定实现见本仓库 `LogFileTraceSegmentServiceClient.isOrphanSegment`。
> **标注**：本文结论来自 agent 源码（skywalking-java @ `47ff1e8`）、本仓库插件源码，以及真实采集样本；无法从上报数据看到的一律标"未核实"。

---

## 0. 一句话

**一次正常请求从 `Entry` span 开始；如果某段是在"没有任何 trace 上下文"的线程上凭空产生的（根是 Exit/Local、没有父引用、也没有 Entry），它就是"孤段"，本插件会把它丢掉。**

---

## 1. 术语表（先认这几个词）

| 词 | 白话 |
| --- | --- |
| trace | 一次完整调用的总账，用一个 `traceId` 串起来 |
| segment（段） | trace 的一段，通常对应"一个线程上跑的一段逻辑"；同 trace 内每段一个 `traceSegmentId` |
| span | 段里的一个动作，分三类：`Entry`（收到请求）、`Exit`（发出调用）、`Local`（本段内部逻辑） |
| refs | "我从谁的哪个 span 续过来的"引用；**跨线程/跨进程**时用来拼父子链 |
| 孤段 | 没有 Entry、也没有父引用、凭空自建的段（下详） |

---

## 2. 先看懂 id 的结构

SkyWalking 的 id（`traceId` 和 `traceSegmentId`）都由三段拼成：

```
<应用实例ID>.<线程ID>.<时间戳*10000 + 序号>
   c76f…c87   .  86  .   17906693971691046
```

- **第一段**：整个 JVM 唯一的实例 UUID（进程级，同一进程所有 trace 都一样）。
- **第二段**：**线程号**。所以两个 id 第二段不同 = 不同线程——这就是 `CrossThread` 的来源。
- **第三段**：时间戳（毫秒）加该线程内的自增序号。

> 出处：`GlobalIdGenerator`（skywalking-java @ `47ff1e8`）：`StringUtil.join('.', PROCESS_ID, Thread.currentThread().getId(), ...)`。

---

## 3. 为什么会"凭空"出现一段（孤段的成因）

agent 在发起一个 client 调用时会走 `ContextManager.createExitSpan`，它先看当前线程有没有 trace 上下文：

```java
AbstractTracerContext context = CONTEXT.get();               // 线程本地（ThreadLocal）
if (context == null) {
    context = EXTEND_SERVICE.createTraceContext(...);        // 没有 → 新建一条 trace
    CONTEXT.set(context);
}
```

- 线程里**有**上下文 → Exit span 挂在当前请求下面（正常请求链）。
- 线程里**没有**上下文 → **新建一条 trace，这个 Exit span 直接当根**（`parentSpanId = -1`），且没有 Entry。

什么时候会"没有上下文"？典型两类：

1. **后台 / 自发起调用**：定时任务、启动线程、连接池/客户端自身的线程、健康检查……没人给它们 `createEntrySpan`。
2. **异步边界丢了上下文**：线程池 / 回调没被 agent 正确传播，轮到真正发请求时 active span 已为空。

像 gRPC 这种异步调用，回调（`onComplete` / `onClose`）会在别的线程用快照续上下文（`capture()` / `continued()`），于是生成 `CrossThread` 子段——最终就形成"一个 Exit 根 + 几个 Local 子段"的孤段 trace。

## 4. 判定规则（插件实际代码）

`LogFileTraceSegmentServiceClient.isOrphanSegment`（`LogFileTraceSegmentServiceClient.java:838`）：

```java
if (obj == null) return false;                          // 拿不到段对象 → 不判孤
if (raw != null && raw.getRef() != null) return false;  // 有父引用 → 异步子段，留
for (span : obj.getSpansList())
    if (span.spanType == Entry) return false;             // 有 Entry → 事务段，留
return true;                                            // 否则 = 孤段，过滤
```

| 根 span | 有 ref？ | 判定 | 典型例子 |
| --- | --- | --- | --- |
| `Entry` | — | **保留** | 正常请求 |
| `Exit` | 有 | 保留 | 跨进程 / 跨线程子段 |
| `Exit` | 无 | **过滤** | 无上下文的 client 调用（如 etcd） |
| `Local` | 有 | 保留 | 异步派发子段 |
| `Local` | 无 | **过滤** | 无上下文的本地自建段 |

> 注意：判定看的是**运行时的 `raw.getRef()`（segment 级）**，不是上报数据里的 span 级 refs。两者语义相关但不同源，详见 `docs/reference/skywalking-trace-refs.md` §2/§3/§7。

## 5. 两种典型原型（真实样本）

### 原型 A：正常请求（**不该误伤**）——两段都保留

样本 trace `c76fbd89…c87.86.17906693971691047`（gisserver，共 2 段）：

| 段 | id 尾 | span | refs |
| --- | --- | --- | --- |
| A | `…86.…1691046` | `Entry` / `GET:/kqgis/rest/services/STK_dir/realspace/data/…1365.terrain` | 无 |
| B | `…100.…1701322` | `Local` / `UndertowDispatch`（log：`forward-url=/STK_dir/…/1365.terrain`） | `CrossThread → A` |

- A 有 Entry → 保留；B 有 ref → 保留。**两段都在**，无悬挂。

**这到底是什么（机制）**：一次 HTTP 请求进来后，应用在**服务器内部做了 forward**（把处理转交给另一个资源），且这次派发被**丢进线程池、在另一个线程执行**。两个特征词都来自 SkyWalking 的 undertow 插件：

- `UndertowDispatch` = `SWRunnable`——派发任务在别的线程被包装执行：
  ```java
  AbstractSpan span = ContextManager.createLocalSpan("UndertowDispatch");
  span.setComponent(ComponentsDefine.UNDERTOW);
  ContextManager.continued(snapshot);   // ← 续上下文 → 生成 CrossThread ref
  runnable.run();
  ```
- `forward-url` = `ForwardInterceptor`——检测到 forward 时把目标 URL 记到当前 span 的 log：
  ```java
  eventMap.put("forward-url", …);
  abstractTracingSpan.log(System.currentTimeMillis(), eventMap);
  ```

- **forward 不一定是你代码里显式的 `.forward()`**：任何组件内部调用 servlet forward 都会命中。**URL 规整过滤器就是典型的隐性来源**——例如 Tuckey `URLRewriteFilter` 的默认重写就是内部转发（`NormalRewrittenUrl`：`getRequestDispatcher(...).forward(request, response)`），所以 `forward-url` 记的往往是"规整 / 重写后的目标 URL"。

**别把它当 redirect**：redirect(302) 会让浏览器发**新请求** → 形成**新 trace、新 Entry**；而 forward 是**同一请求**内部转交 → **同一 trace**（跨线程时只多出一个段）。所以"同 traceId、同 serviceInstance、`CrossThread` 相连"就是 forward 的标准长相。

**原始 JSON（2 段）**：全文见 §9.A。

### 原型 B：孤段（**该过滤**）——根被过滤

样本 trace `c76fbd89…c87.261.17906685376240017`（gisserver，共 3 段）：

| 段 | id 尾 | span | refs |
| --- | --- | --- | --- |
| R（根） | `…261.…240016` | `Exit` / `etcdserverpb.KV.range` | 无 |
| C1 | `…63.…242696` | `Local` / `etcdserverpb.KV.range/client/Response/onClose` | `CrossThread → R` |
| C2 | `…261.…240018` | `Local` / `etcdserverpb.KV.range/client/Request/onComplete` | `CrossThread → R` |

- 全 trace **没有任何 Entry**；根 R 是 `Exit` 且无 ref → **判孤、过滤**。
- C1 / C2 有 ref → 保留。

**原始 JSON（3 段）**：全文见 §9.B。

### 副作用：过滤后会留下"悬挂子段"

R 被过滤后，C1 / C2 的 `parentTraceSegmentId` 仍指向 R（已不存在）。这不是 bug——判定只看"根 span 类型 + 有无 ref"，**不看它是否被别的段引用**。排查"子段还在、父段没了"的现象时，成因就在这里。

---

## 6. 小白速查：拿到一条 trace 怎么判

1. 有 `Entry` span 吗？有 → 正常请求，保留。
2. 没有 Entry，但某段有 `refs`？→ 它是异步子段，保留。
3. 根是 `Exit` / `Local`，且**没有 ref、也没有任何 Entry**？→ 孤段，会被过滤。

## 8. 证据与边界

- **Agent 源码**：`ContextManager`（`createExitSpan` → `getOrCreate` → 无上下文则新建 trace）、`GlobalIdGenerator`（id 三段）—— skywalking-java @ `47ff1e8`。
- **插件判定**：本仓库 `LogFileTraceSegmentServiceClient.java:838`。
- **Undertow 转发/派发**：`SWRunnable`（operation `UndertowDispatch`、`createLocalSpan` + `continued`）、`ForwardInterceptor`（log `forward-url`）、`RequestDispatcherImplInstrumentation`（match `RequestDispatcherImpl#forward`）—— undertow-2.x-plugin，skywalking-java @ `47ff1e8`。
- **URL 规整转发**：Tuckey `urlrewritefilter` 的 `NormalRewrittenUrl`（`isForward()` → `getRequestDispatcher(...).forward(...)`）。
- **真实样本**：采集文件 `F:\_test\12LQ.txt`（本地导出，单一 JSON：`{"data":{"<traceId>":{"logs":[SegmentObject…]}}}`），时间窗约 `15:55:37 – 16:25:37`；共 **2000 个 traceId / 5940 个段**，其中**无 Entry 的 218 个**（根 span：`Local` 142、`Exit` 76）。原始样例全文见 §9 附录。
- **未核实**：`raw.getRef()` 是运行时段级字段，上报数据里看不到；样本中"根无 span 级 ref"是推断其段级 ref 也为空的依据。要 100% 坐实，需在 agent 侧对根段打点 `raw.getRef()`。
