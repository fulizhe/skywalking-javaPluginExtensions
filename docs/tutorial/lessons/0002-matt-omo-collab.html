matt-skills 与 OMO 协同

目标：你说清谁管什么，任务来了能立刻判断该用哪套。

先记结论：matt-skills 是主体（管"做什么、怎么算完"），OMO 是补短板（管"怎么又快又省地探索+实现"）。 不是二选一，是上下游。

一、一张表看懂分工

层级谁管什么用哪套工具
主体 matt-skills 需求 → spec → ticket → 验收 的完整流程 /to-spec、/to-tickets、/triage、/wayfinder、/code-review、/domain-modeling
补短板 OMO 扫大库、查文档、深逻辑、后台并行、续跑 ultrawork/ulw、task(explore/librarian)、Sisyphus 编排、codegraph/LSP
matt-skills 决定"打哪里、怎么算赢"；OMO 决定"怎么又快又省地摸清战场、把活干完"。

二、你配置里那行开关（为啥这么设）

"sisyphus_agent": { "disabled": true }

disabled: true = Sisyphus（OMO 自动总控）不接管主对话。这是保住 matt-skills 主体地位的关键：

  • ✅ 保住主体：build/plan 不被降级，matt-skills 的 /to-spec、/to-tickets 能正常跑
  • ✅ OMO 底层照常在：11 个 discipline agent（Oracle/Librarian/Explore…）、task() 工具、后台探索、codegraph 都在
  • ⚠️ OMO 全自动编排要手动触发：敲 ultrawork/ulw，或手动切到 sisyphus

三、matt-skills 主体工作流（这个项目怎么走）

载体都在仓库里：spec/ticket 在 .scratch/<feature>/，术语+ADR 在 CONTEXT.md + docs/adr/，triage 标签在 docs/agents/triage-labels.md。

/to-spec             把想法变成 spec
/to-tickets          拆成带依赖的 ticket（01,02…）
/triage              给 ticket 标状态
/domain-modeling     /grill-with-docs 沉淀术语 + ADR
/implement           按 ticket 实现
/code-review         按规范 + 对照 spec 验收

四、OMO 补的短板（对照表）

你遇到OMO 补什么怎么触发
要扫一遍大库找代码explore 后台并行搜，不占主上下文说要"探索"或 task(explore)
要查外部文档/开源实现librarian 子 agent说要"查文档/开源"
实现时深逻辑/跨文件ultrabrain / deep / Sisyphus 编排ultrawork 任务
卡壳的架构/疑难oracle（只读顾问）说要问 oracle
长工程中断要续跑计划续跑（断点续）Prometheus → /ulw-execute
视觉/前端visual-engineering 分类task(category="visual-engineering")

五、决策表：任务来了选哪条

目标 = "把需求落地成工程"     → 用 Build / Plan（matt-skills 主体：to-spec → to-tickets → …）
                            └─ 途中要探索/查资料/深分析/并行 → 临时调 OMO 补
目标 = "一个具体实现/修复，求快" → 切到 Sisyphus - Ultraworker（或 Build 上打 ultrawork）
目标 = "复杂多步，要精准"      → Plan 规划 → Atlas - Plan Executor 执行（/ulw-execute）
你的 4 个 agent 一键对应三档：Build=直接打字、Sisyphus - Ultraworker=全自动、Plan→Atlas - Plan Executor=精准编排。都在左下角下拉里选，不用背命令。

六、真实例子（skywalking 项目）

给活跃模块 logfile-reporter-plugin 加功能：

  1. matt-skills 启动：/to-spec → /to-tickets → 落 .scratch/
  2. 中途探索：「用 explore 把 logfile 核心类扫出来」（OMO 后台跑）
  3. 实现：照 ticket 改，或 ulw 按 ticket 02 实现
  4. 验收：/code-review 对照 spec
  5. 卡壳 → 问 oracle；深逻辑 → ultrabrain

练一下

① 要"把想法写成 spec 并拆成 ticket"，该用哪套？
matt-skills（/to-spec → /to-tickets）。这是主体工作流。
② 实现中"不确定改哪几个文件，想快速扫一遍大库"，该用哪套？
OMO 的 explore/探索能力（后台并行扫，不占主上下文）。这是 OMO 补的短板。
③ 为什么 sisyphus_agent.disabled: true？
让 Sisyphus 不自动接管，保住 matt-skills 的 build/plan 主体地位；OMO 底层能力仍可用，全自动编排靠 ultrawork/ulw 手动触发。
