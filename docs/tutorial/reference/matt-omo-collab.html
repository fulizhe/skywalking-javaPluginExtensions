matt-skills 与 OMO 的分工与协同

matt-skills 是主体工作流（管「做什么、怎么做完」），OMO 是补短板（管「怎么高效探索、怎么并行、怎么续跑」）。

一句话分工

层级谁管什么用哪套工具
主体 / 上游matt-skills需求 → spec → ticket → 验收 的完整工程流程/to-spec、/to-tickets、/triage、/wayfinder、/code-review、/domain-modeling
补短板 / 下游OMO低成本深度探索、跨上下文/大库扫描、后台并行 agent、计划续跑、LSP/codegraphultrawork、ulw、task(explore/librarian)、Sisyphus 编排
matt-skills 决定你「做什么」「做到什么算完」；OMO 决定你「探索和实现时快不快、省不省力」。 两者不是竞争，是上下游。

为什么这样分（你的配置已经这么做了）

你的 .omo/omo.jsonc 里这一行是整套协同的开关：

"sisyphus_agent": { "disabled": true }

disabled: true 的意思是：Sisyphus（OMO 的自动总控）不接管主对话。代价/收益——

  • ✅ 保住 matt-skills 的主体地位：build/plan 不被降级成隐藏子 agent，/to-spec、/to-tickets 能正常跑
  • ✅ OMO 的底层能力照常可用：11 个 discipline agent（Oracle/Librarian/Explore…）、task() 工具、后台探索、codegraph、LSP 全都在
  • ⚠️ 想用 OMO 的全自动编排，要手动敲 ultrawork/ulw，或手动切到 sisyphus agent——不会自动抢
注意：disabled_agents: ["hephaestus"] 是因为只有 opencode-go 一家 provider，而 Hephaestus 只能用 GPT 系列，环境不允许，所以显式禁用避免白撞。

matt-skills 主体工作流（你项目里怎么走）

这套流程的载体都在仓库里：spec / issue tracker 在 .scratch/<feature-slug>/，triage 标签在 docs/agents/triage-labels.md，领域术语 + ADR 在 CONTEXT.md + docs/adr/，领域文档消费约定在 docs/agents/domain.md。

/to-spec        ← 把想法变成 spec（写到 .scratch/<feature>/spec.md）
/to-tickets     ← 把 spec 拆成带依赖的 ticket（issues/01-*.md, 02-*.md…）
/triage         ← 给 ticket 标状态（ready-for-agent 等）
/domain-modeling / /grill-with-docs ← 需要时沉淀术语 + ADR
/implement      ← 按 ticket 实现
/code-review    ← 按规范 + 对照 spec 验收

OMO 补的短板（matt-skills 缺/弱的地方）

matt-skills 场景OMO 补什么怎么触发
要扫一遍大库找相关代码OMO 的 explore 子 agent 后台并行搜索，不占用主上下文@explore 或 task(explore)
要查外部文档/开源实现librarian 子 agent（搜 GitHub、官方 API、OSS 示例）@librarian 或 task(librarian)
实现时跨文件、深逻辑ultrabrain / deep 分类，或 Sisyphus 全编排ultrawork 任务
卡壳时架构/疑难问题oracle（只读顾问）@oracle
长工程被中断要续跑OMO 的计划续跑（.omo/boulder.json、/ulw-execute 断点续）Plan 规划 → /ulw-execute
视觉/前端工作visual-engineering 分类（自动路由到前端模型）task(category="visual-engineering")

什么时候用哪个 —— 决策表

你的目标是「把需求落地成工程」 → matt-skills 主体（to-spec → to-tickets → …）
                                  └─ 过程中要「探索/查资料/深度分析/并行」→ 临时调 OMO 补
你的目标是「一个具体实现/修复，想快」 → 切到 Sisyphus - Ultraworker（或 ultrawork 一把梭）
你的目标是「复杂多步，要精准」      → Plan 访谈 → /ulw-execute

一个真实例子：在 skywalking 项目里

比如要给 logfile-reporter-plugin（活跃模块）加个功能：

  1. matt-skills 启动：/to-spec 写 spec → /to-tickets 拆 ticket → 落 .scratch/
  2. 中途探索：不确定改哪几个文件 → @explore 帮我把 logfile 核心类扫出来（OMO 后台跑）
  3. 实现：照 ticket 改（主 agent 干，或 ulw 按 ticket 02 实现）
  4. 验收：/code-review 对照 spec + 仓库规范
  5. 卡壳 → @oracle；深逻辑 → ultrabrain

一句话记住

matt-skills 决定「打哪里、怎么算赢」；OMO 决定「怎么又快又省地摸清战场、把活干完」。 你永远是主体工作流的掌舵人，OMO 只在需要时被叫来帮忙。
