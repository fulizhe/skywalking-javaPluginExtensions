术语表

SkyWalking Java test/ 模块词汇 + 可移植集成测试模式词汇。课程全程以本表为准。

怎么用这张表。 分两部分：A 部分是读上游源码时必须认得的专有名词 （不认得就看不懂代码）；B 部分是这套设计背后的可迁移模式，带「在别处叫什么」一栏—— 迁移到自己的 Java / Go 项目时靠这一栏对上号。代码、字段名、路径一律保留英文原样。
基准版本：apache/skywalking-java @ ea2fb09（main）。
一手来源见 RESOURCES.md。

速查：A · 上游专有名词

结构与运行

scenario · 场景

test/plugin/scenarios/ 下的一个独立 Maven 项目，是这套框架的测试单元。 它自带一个被测应用（fat-jar 或 WAR）、一份配置、一份预期数据、一个版本矩阵。

读法：scenario 不是「一个测试方法」，而是一整套可独立运行、可独立判定成败的验证装置。

configuration.yml · 场景配置

声明怎么跑这个场景。由 runner-helper 翻译成实际的 docker run 或 docker-compose 调用。字段：type（jvm / tomcat）、 entryService、healthCheck、startScript、runningMode、 withPlugins、environment、dependencies。

POJO 定义见 …/vo/CaseConfiguration.java。

expectedData.yaml · 预期数据

声明必须产生什么。整套框架的心脏：一份描述期望上报内容的 YAML，由通用匹配引擎 （skywalking-validator）与实际抓到的数据逐字段比对。三大类： segmentItems（链路）、meterItems（指标）、logItems（日志）。

这是本课程最可迁移的一个概念。计划在第 2 课《声明式预言》展开。

actualData.yaml · 实际数据

容器内 mock collector 抓到的真实上报内容，由框架生成而非手写。 校验通过会被删除；要看它得加 --debug。这是「声明式预言」能自我纠错的关键： 失败时把预言和现实并排摆给你看。

mock collector · 模拟收集端

容器内监听 19876 端口的 gRPC 服务，冒充 OAP 接收 agent 上报的 span / meter / log， 并落成 actualData.yaml。它的存在让 plugin 测试不需要真的跑 OAP—— 这是「快」这一节的全部秘密。

validator · 校验器

skywalking-validator.jar，容器内最后一步。读 expectedData.yaml 与 actualData.yaml，按规则引擎逐项比对，退出码即 scenario 成败。

关键点：断言逻辑是通用的、与被测插件无关的一份代码。所以新增 scenario 只需写 YAML，不用写 Java —— 这是「声明式」带来的直接收益。

entryService · 入口服务

触发场景的 URL。容器 run.sh 用 curl -s --max-time 3 打它，且没有预热。 所以第一个冷请求必须在 3 秒内完成，否则整场失败。这是本框架最著名的坑。

别和 e2e 的 trigger 混起来：trigger 是 YAML 里的一个阶段， entryService 是 plugin 容器的硬编码单次请求。

healthCheck · 健康检查

就绪探测 URL，用 HTTP HEAD（不是 GET）访问。自写的健康检查端点必须处理 HEAD 请求。

agent_opts · agent 启动参数

type: jvm 场景里，bin/startup.sh 必须包含 java -jar ${agent_opts} …。框架通过这个占位符注入 -javaagent: 行。 漏掉它 → agent 根本没挂上 → 场景必然失败，且失败信息会误导你去查插件逻辑。

support-version.list · 版本矩阵

纯文本，一行一个版本，# 注释。run.sh 逐行遍历，每版构建并跑一遍场景。 规则：每个 minor 取最新补丁，不是每个补丁都测。支持行尾附加 Maven 属性 （2.7.14,spring.boot.version=2.5.15）。

base image · 基础镜像

--base_image_java / --base_image_tomcat 指定。 版本钉在 CI 泳道里，不在 configuration.yml 里—— configuration.yml 只说 type: tomcat，用哪个 Tomcat 版本由所在泳道决定， 同泳道所有 scenario 共享一个镜像。

这是「测试声明需要什么，流水线决定怎么满足」的分离思想。见下方 test ladder 相关条目。

CI lane · 泳道

.github/workflows/plugins-<jdk>-test.<n>.yaml，一个文件一条泳道。 它的 build job 钉 base_image_java + base_image_tomcat， test job 的 matrix.case 列出本泳道跑哪些 scenario。 尾号 .0 / .1 只是分桶限流。新增 scenario 用 tools/select-group.py 找最闲的桶。

硬约束：jakarta 系的 WAR（Struts 7 / Jetty 12 / Spring 6）必须挂到 JDK-17 泳道（Tomcat 10.1 基座），javax 系的挂老泳道。挂错池子 = 部署不上去。

workspace · 运行工作区

test/plugin/workspace/<scenario>/<version>/，每次运行的产物落点， 含 logs/ 与 data/actualData.yaml。--cleanup 清除。

领域数据（SkyWalking 自己的词汇）

segment · 链路片段
一次「进程内的一组 span」的单位，SkyWalking 特有的中间层（trace → segment → span 三级）。 对应 OpenTelemetry 的 span 本身，少了一层聚合。
span
最小工作单元。spanType：Entry（入站，被调用方）/ Exit（出站，调用方）/ Local。spanLayer： Http / DB / RPC_FRAMEWORK / MQ / CACHE。 parentSpanId: -1 表示根 span。
refs · 跨进程引用

一个 segment 携带的「我被谁调过来的」上下文。关键字段 refType: CrossProcess、parentEndpoint、parentSpanId、 parentTraceSegmentId、parentService、traceId。 它是「跨进程传播是否生效」的唯一证据，也是最常被漏断言的字段。

要区分两个 span：spanId 是 segment 内序号（0,1,2…）； parentSpanId 指向同 segment 内的父；跨进程则靠 refs，不靠 parentSpanId。

componentId · 组件 ID
插桩点标识。断言 componentId 等于断言「这个请求确实是被这个插件插的桩」， 比断言 operationName 更能防张冠李戴。
tags
span 上的键值对：url、http.method、http.status_code、 http.params、http.headers、db.*。 插件的「取数据逻辑」就体现在这里，所以断言 tags 是断言插件真的读到了字段。

匹配算子（宽松匹配语义）

rule / 匹配算子

expectedData.yaml 里每个值都可以不是字面量，而是一条规则。 数字：eq（默认）ne gt ge； 字符串：eq（默认）not null not blank null start with end with；还有 nq（not equal，用于时间戳）。

为什么必须宽松：traceId、segmentId、耗时都是运行时生成的，不可能写死。 宽松是被迫的，不是偷懒——但它有代价（会漏掉「值变了但仍满足规则」这类回归）。 这条取舍值得单独想清楚。

B 部分 · test/e2e 的词汇

e2e.yaml
全栈测试的编排文件，三段式：setup（env / compose 文件 / timeout / init 步骤）→ trigger（发流量）→ verify（带重试的查询 + 期望文件比对）。 verify.retry 是必需的，因为 OAP 写入是最终一致的。
swctl
SkyWalking CLI。verify 段用它发 GraphQL 查询并 --display yaml 输出， 再与 expected/*.yml 比对。断言对象从「agent 上报了啥」变成「OAP 存进去啥」。
base-compose.yml
test/e2e/base/ 里的模板：OAP + BanyanDB + provider + consumer。 具体 case 的 compose 继承它再加自己的东西——整套环境是模板化的，不手写。
BanyanDB
SkyWalking 的原生存储后端。e2e 之所以重，就是因为它要把真实 OAP + 真实存储整套拉起来。

速查：B · 可迁移模式词汇

这一栏是本课程的真正交付物。「在别处叫什么」列用于迁移到别的项目/生态时对上号。

模式含义在别处叫什么
场景即测试
scenario-as-test		 当代码的风险来自「与真实第三方框架交互」时，跑真框架的集成场景就是充分测试； mock 单元测试在结构上无法覆盖该风险。上游明确劝退为插件堆 mock 单测。 Testing on the Boundary（Michael Feathers）；Google 的「小/中/大」测试分级里只允许少量 mock 掉自己的代码
声明式预言
declarative oracle		 把「期望」写成数据（YAML），交给一份通用引擎比对，而不是散落在代码里的 assertEquals。好处：新增测试只写数据；失败时预言与现实并排可比对。 Approval Tests、Jest snapshot、golden file、Pact、k6 threshold、Terraform plan test
宽松匹配
loose matching		 对无法预测的字段（ID、时间戳、耗时）用算子而非字面量。被迫之举，但必须显式： 哪些字段放宽、为什么放宽，都是要写在文件里的决定。 容差断言 / property-based testing 的 matcher；OpenAPI 的 schema 级校验
假通过
vacuous pass		 测试通过但其实没测到东西。最常见的两种：只断言了「有 span」而不断言 refs（等于没测传播）；segmentSize 用 ge 却没想清楚下限。 mutation testing（变异测试）专门用来暴露它；覆盖率工具的盲区
密闭环境
hermetic environment		 测试自带完整依赖，不依赖开发机状态。代价是慢，所以只对需要真实依赖的部分用。 Testcontainers、docker-compose 测试、WireMock、Go 的 httptest
测试阶梯
test ladder		 单测（快、窄）/ 场景测试（中、验证组件对真实框架的行为）/ 全栈 e2e（慢、验证组件之间的接线）。 每一级回答不同的问题，不是同一件事的重复三遍。 Google Test Sizes（小/中/大）；测试金字塔的修正版——关键差别在「各级回答不同问题」
版本即矩阵
version matrix		 把「兼容哪些版本」写成可执行的数据（support-version.list）， 由 runner 遍历——文档与测试合一，不会腐烂。 CI 的 version matrix（GitHub Actions）、测试容器的 image tag 矩阵、 Renovate/Dependabot 的 version range
声明需要 ≠ 决定如何满足
declare vs provide		 scenario 只说 type: tomcat，不选 Tomcat 版本；版本由 CI 泳道注入。 测试声明需求，流水线决定供给，从而同一份测试能在不同环境复用。 依赖注入、12-factor 的 config、Terraform 的 variable vs provider、 Testcontainers 的 ImageFromDockerfile 抽象
脚手架即框架的一部分
scaffold		 框架自带「30 秒新建一个测试」的命令（generator.sh + Maven archetype）。 没有它，框架的采纳率会被「不知道从哪抄一个」卡死。 go test 脚手架、Spring Initializr、cargo new、 Django 的 startapp、Testcontainers 的 ryuk 之类自举工具
变异检验
mutation check		 故意把被测代码改坏，验证测试会变红。绿色的测试如果改坏代码后还绿，它什么都没测。 这是唯一能证明「我的测试有效」的手段。 PIT / mutation testing 工具；「characterization test」的验证方式； 混沌工程（把依赖搞坏看系统是否发现）
非确定性是资源问题
cold start budget		 密闭测试仍是真实系统：3 秒冷启动超时、JIT 预热、JSP 冷编译、覆盖率插桩开销。 失败常是环境预算不足，不是代码 bug。诊断顺序：先怀疑环境，再怀疑代码。 Fowler 的 non-determinism 分类；测试的 time budget / retry 策略； Go 的 -race 与 -count 放大
