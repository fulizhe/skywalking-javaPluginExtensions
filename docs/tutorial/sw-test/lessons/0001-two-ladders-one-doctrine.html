第 1 课 · 两个测试台，一条信条

读懂 apache/skywalking-java/test 的全貌，以及它背后那条真正值钱的设计主张。

本课战果。 看完这一课，你能打开 test/plugin/scenarios/ 下任意一个目录， 在 5 分钟内说清三件事：它声明了什么、它断言了什么、为什么这两件事被严格分开。 并且能解释为什么这套东西不用 mock 单元测试。

第 1 课 · 约 10 分钟 · 无需动手环境，先读懂结构

一、先纠正一个直觉：test/ 不是「一个测试模块」

你给的链接里只有一个 test/ 目录，很容易以为它是一套东西。实际上它是两台 完全不同的机器，服务两种不同的问题：

test/plugintest/e2e
回答的问题 「这个插件插桩对不对？兼容哪些版本？」 「整条链路接通了吗？」
真相从哪来 容器内一个假的 OAP（mock collector，端口 19876）接收 agent 真实上报的数据 真的拉起 OAP + BanyanDB，再用 swctl 发 GraphQL 查回来
粒度 一个 scenario = 一个插件 × 一组版本 一个 case = 一套 provider / consumer 组合
量级与耗时 200+ scenario，每个几分钟 少数几个 case，每个十几到几十分钟
谁该写 插件作者（加插件就加它的 scenario） 框架/OAP 侧的人（验证组件之间的接线）
选哪台机器，看你要回答的问题落在哪一格。 大多数人第一次接触时想用 test/e2e，因为它看起来「更完整」。但如果你要验证的是 「我写的插件有没有正确地把 span 打出来」，那 test/e2e 是过度的： 它要为一件事拉起一整套 OAP。选错阶梯的代价是慢到没人愿意跑。

二、那条信条：场景就是测试

Apache 自己在 test/plugin/CLAUDE.md 里的原话很直接：

「对一个 agent 插件来说，插件测试场景就是那个主要且充分的测试。 不要为了插件过度设计、堆一堆单元测试。」

— test/plugin/CLAUDE.md，Testing philosophy

为什么这么绝对？因为一个插桩插件的真实风险只有两处，而这两处 mock 在结构上就测不到：

风险一：cast / 取数据逻辑

插件把拦截到的参数强转成框架类型，再从上面读 header、method、URI、status、param。 如果框架的实际类根本没有你以为的那个方法，或者某个版本换了包名——你的 mock 写得再对也照样绿，因为 mock 里那个类是你自己造的那个类。mock 只能证明 「代码符合我对框架的假设」，证不了「假设成立」。

风险二：版本兼容

同一份 interceptor 要在 N 个版本上工作。mock 是你挑的版本，它对不对全凭你自觉。

关键洞察。 跑一次真框架的 scenario，把上面两件事同时证明了—— 因为真实类真的被加载了、真实版本真的被增强过。一次运行，两份证据。 这就是为什么他们敢劝退 mock 单测：不是嫌 mock 差，是嫌 mock 在这里信息量为零。

对照你自己的仓库看这个道理

你不用相信我，去看自己代码——反面例子就摆在这儿：

logfile-reporter-plugin含义
mock 单元测试约 169 个证明逻辑分支被覆盖
场景断言（verify/）24 条证明端到端行为对

169 比 24，多出来的那 145 条在测「我的代码按我以为的方式运行」。它们不是没价值 （重构护栏、分支覆盖），但它们没有一条能证明「agent 增强之后，interceptor 真的从 真实的 logback 对象上读到了它要的东西」。那是 verify/ 那 24 条干的活。 数量和覆盖风险完全是两回事——这是本课最该带走的一句话。

三、精读：一个 scenario 的两份契约

框架自带两个 Maven archetype（jvm 和 tomcat）， generator.sh 就是拿它们生成新 scenario 的。所以 archetype 就是 scenario 的 标准合同——比任何真实 scenario 都干净，没有框架特有的噪声。看 tomcat 那个：

archetypes/tomcat/…/archetype-resources/ ├── configuration.yml ← 契约一：声明「怎么跑」 ├── config/ │ └── expectedData.yaml ← 契约二：声明「必须产生什么」 ├── support-version.list ← 声明「跑哪些版本」 ├── pom.xml └── src/main/ ├── java/ │ ├── CaseServlet.java 被测入口 │ └── HealthCheckServlet.java 健康检查（注意：处理 HEAD） ├── resources/log4j2.xml └── webapp/WEB-INF/web.xml

契约一：configuration.yml —— 只说「怎么跑」

下面是 archetype 里的原文（只剥掉了 Apache license 头，${…} 是 archetype 模板变量，generator.sh 会替换掉）：

type: tomcat
entryService: http://localhost:8080/${scenario_name}/case/${scenario_case}
healthCheck: http://localhost:8080/${scenario_name}/case/healthCheck
environment:
dependencies:

注意它刻意不写什么：不写 Tomcat 版本，不写 JDK 版本，不写期望的 span。 这三样分别由 CI 泳道、support-version.list 和 expectedData.yaml 负责。 配置只回答「把这个东西怎么启动起来、然后敲哪个 URL」。

契约二：config/expectedData.yaml —— 只说「必须产生什么」

同样是 archetype 原文，几乎是空的——因为框架不知道你要插什么桩：

registryItems:
  services:
    - {${scenario_name}: 2}
  instances:
    - {${scenario_name}: 1}
  operationNames:
    - ${scenario_name}: []
  heartbeat: []
segmentItems:
  - serviceName: ${scenario_name}
    segmentSize:
    segments:

四类断言对象：registryItems（服务/实例注册）、segmentItems（链路）， 后面还有 meterItems（指标）、logItems（日志）。 你的测试代码一行断言都不写——你写的是一份数据，通用引擎拿它去比对容器里抓到的真实上报。

这份「两份契约严格分离」是整套设计里最值钱的东西。 环境怎么来和数据应该长什么样，是两个正交的变化轴。改断言不碰环境，改环境不碰断言。 这个模式的名字叫声明式预言，第 2 课专门拆它。

真实的 expectedData.yaml 长什么样：看那个 refs 块

上面是空模板。真要看「断言完整形状」是什么意思，看 struts2.7-scenario 的 config/expectedData.yaml（原文节选）：

segmentItems:
- serviceName: struts2.7-scenario
  segmentSize: gt 2
  segments:
  - segmentId: not null
    spans:
    - operationName: /struts2.7-scenario/case/case1.action
      parentSpanId: -1
      spanId: 0
      spanLayer: Http
      startTime: gt 0
      endTime: gt 0
      componentId: 15
      isError: false
      spanType: Entry
      peer: ''
      tags:
      - {key: url, value: 'http://localhost:8080/struts2.7-scenario/case/case1.action'}
      - {key: http.method, value: GET}
      - {key: http.status_code, value: '200'}
      refs:
      - {parentEndpoint: /struts2.7-scenario/case/case.action, networkAddress: 'localhost:8080',
        refType: CrossProcess, parentSpanId: 1, parentTraceSegmentId: not null,
        parentServiceInstance: not null, parentService: struts2.7-scenario, traceId: not null}

这个场景打的是 curl → case.action → 它自己发起的 HttpClient 调用 → case1.action， 所以真实链路上有 2 个 entry + 1 个 exit。而 case1.action 上这个 refs 块是整份文件里最值钱的 8 行：

它证明了「跨进程上下文真的传过去了」。 没有 refs，case1.action 就是一个孤立的 span，和 case.action 没有任何关系——你测的其实是两个独立的东西。 上游把这叫假通过：CLAUDE.md 原话是「断言了 span 却不断言 ref 的 scenario，并没有证明传播」。

顺带注意值不是字面量：not null、gt 2、gt 0。 traceId、segmentId、耗时都是运行时生成的，写死就永远失败。所以宽松匹配是被迫的—— 但被迫不等于随意：哪些字段放宽、为什么放宽，是写在文件里的显式决定，不是默认值。 这条取舍第 2 课细讲。

顺带一个必知细节：type: jvm 的 startup.sh

fat-jar 场景（type: jvm）的 bin/startup.sh 原文只有一行有效代码：

home="$(cd "$(dirname $0)"; pwd)"
java -jar ${agent_opts} ${home}/../libs/${scenario_name}.jar &

${agent_opts} 那个占位符不能删。框架靠它注入 -javaagent: 行； 删了它 agent 根本没挂上，场景必挂，而且失败信息会把人引到「去查插件逻辑」这个错误方向上。 这类失败信息误导的坑，是密闭测试框架的典型副作用，后面第 3 课实跑时会撞到更多。

四、检索练习

先别往下看，闭眼答一遍。这两条是本课的骨架。

1. test/plugin 判定一个 scenario 通过与否，最终取决于什么？

为什么。 启动成功、健康检查通过、jar 打进包了——这些都是必要条件， 框架内部逐步检查，任何一步不过都会在更早的地方退出。它们都不构成「通过」的定义。

「通过」的唯一定义是最后一步：skywalking-validator 拿 expectedData.yaml 和容器里 mock collector 抓到的真实数据比对，全部满足才退出 0。 注意 D 项是真的会被检查的（PLUGIN_LOAD_REGEX 之类）， 但它是「插件有被加载」而非「插件行为正确」——这是最容易被混为一谈的两个命题。

2. 断言「跨进程传播生效」时，最不能省的是哪一项？

为什么。 A 是唯一能区分「两个独立请求」和「一次调用链」的证据。 没有 refs，你断言的 2 个 entry span 可能来自两次毫不相干的独立请求， 测试照样绿——这就是假通过。

C 有价值（peer 说明 exit span 指对了目标），但它只证明「知道往哪发」， 不证明「对面收到了我是谁」。B 是性能断言，和传播正交。 D 恰恰是陷阱：真实环境里 agent 自己的健康探测也会产生 segment，所以 segmentSize 必须用 ge 而不是 eq—— 写成 eq 会得到一个偶发失败的测试，比没有更糟。

五、5 分钟动手：验证你真读懂了

不要跳。合上上面的内容，自己做三件事：

  1. 打开 scenarios/httpclient-4.3.x-scenario， 读它的 configuration.yml 和 config/expectedData.yaml。
  2. 回答：它有没有 refs 块？为什么应该有还是没有？ （提示：看 type 和它的应用形态。）
  3. 然后做真正有价值的对照：打开你仓库的 verify/scenarios/override-httpclient/checks.sh， 找出它里面等价于「断言 http.request.params 这个 tag」的那一条命令， 写下来。
第 3 步是本课的真正作业。 上游写 - {key: http.params, value: '...'}（一行声明）； 你的 checks.sh 要写一串 jq 管道去从应用接口的返回里刨出同一个事实。 同一个断言，两种范式——声明式 vs 命令式。 这就是第 2 课要拆的东西，也是你能带走的最直接的一件工具。

六、这在别处叫什么（可迁移性）

你说这门课要能用到别的 Java 项目、甚至 Go 项目上。那就逐条对上号——学到模式， 而不是学到 API：

本课看到的换个名字你可能已经认识
「场景即测试」，劝退 mock 单测 Testing on the Boundary （Michael Feathers）；Google 的「小/中/大测试」分级——核心主张一致：不要 mock 你要测的那一层。 Go 生态对应 httptest + 真依赖，而非 mock 掉自己的 handler
expectedData.yaml 当预言 Approval Tests、Jest snapshot、 Go 的 golden file、Pact 契约文件—— 全都是同一个形状：期望写成数据，交给通用引擎比对
宽松匹配算子（not null / gt） 容差断言；OpenAPI schema 级校验；property-based testing 的 matcher
「不断言 refs 就是假通过」 变异测试存在的全部理由： 一个改坏了代码还绿的测试，等于没测
mock collector 冒充 OAP Testcontainers + WireMock / Mountebank / gRPC test server。Java 用 Testcontainers，Go 用 testcontainers-go
版本钉在 CI 泳道，不在配置里 依赖注入、Terraform 的 variable/provider 分离、12-factor 的 config 原则
generator.sh + archetype 脚手架即框架的一部分。Go 的 go test 模板、Spring Initializr、 cargo new。没有脚手架的框架，采纳率会死在「不知道从哪抄一个」
