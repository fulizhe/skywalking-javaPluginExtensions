Worth exploring in-process

Before — 一个 module 混四种关切

After — 诊断收进一个 owner
TraceAlertMetrics → 纯 counters

Problem. TraceAlertMetrics（287 行）把 counters、config 快照、webhook 诊断、rules 快照混在一处，还直接读 RulesEngine 内部；「webhook URL 是否仍是未解析占位符」在 3 处独立重算。

  • locality：webhook 判定单点
  • interface 缩小：counters 与诊断分家
  • narrow 对 RulesEngine 内部的读

3 · 告警分发器：抽纯 NotifyDecision + 死配置

Worth exploring in-process
AsyncTraceAlertDispatcher.java · LogFileReporterPluginConfig.java
Before — 五关切挤在一个线程类里（无测试）
afterTraceMerged { dedup; snapshot; evaluate; shouldNotify; offer; }
resolveDispatchQueueSize → hardcode 512
After — 纯决策可脱离线程单测
NotifyDecision(snapshot) → EnumSet<AlertType>
dispatcher shell：queue + thread + listener fan-out
DISPATCH_QUEUE_SIZE 接 config 或删

Problem. afterTraceMerged 内联混了 dedup 短路、快照、evaluate、per-type shouldNotify、事件构造、入队——是告警包里唯一并发敏感却没测试的类；resolveDispatchQueueSize 把 config 读注释掉、硬编码 512。

Solution. 拆成纯 NotifyDecision（snapshot → 待通知 EnumSet<AlertType>，无线程无队列可单测）加一个薄 dispatcher shell；把 DISPATCH_QUEUE_SIZE 接进 LogFileReporterPluginConfig 或删掉死注释。

  • locality：决策从线程类里搬出来
  • 可测的 decision 内核
  • 死 config knob 现形

5 · 四个 override sink 复制同一惯用法

Speculative in-process
JVMMetricsLocalSender.java · MeterLocalSender.java · ProfileSnapshotLocalSender.java · LogReportServiceLocalClient.java · CircularBlockingQueue.java
Before — 四份 copy-paste
JVM (cap 1000) Meter (300) Profile (500 hardcode) Log (1000)
各自 build*Map + bounded queue + getX() 快照
After — 一个 adapter + 类型化快照
LocalSink<T>：bounded ring + snapshot read
converter：protobuf → Map（各流一条）
status-expose 收 1 个 typed snapshot 而非 6 次反射
⚠ ADR-02 已把 4 个环形 sender 划为「不在活跃变更路径」并有意保留弱一致快照。仅当它们重新进入变更路径时重开此议题。

Problem. 四个 sink 各自手写 protobuf→Map + 有界队列 + 快照 getter，容量 1000/300/500/1000 不一致，ProfileSnapshotLocalSender 干脆没有 config key。

Solution. 一个 LocalSink<T> adapter 收掉「bounded ring + 快照读」，各流只留一条 converter；status-expose 从 6 次反射 getter 缩成一次 typed 快照。

  • leverage：一个 adapter，四个 sink
  • 删 CircularBlockingQueue 未用的 take/poll 面
  • 反射耦合（seam 泄漏）收缩

6 · collect 决策去中心化：profiling fallback 是死代码

Strong in-process
HttpClientExecuteInterceptor.java · HutoolHttpRequestInterceptor.java · HttpClientParamCollector.java · HutoolHttpParamCollector.java
Before — 决策在两处，内层压过外层
interceptor.beforeMethod：读 switch 决定 collect
interceptor.afterMethod：profiling fallback 强制 collect
collector.collect()：再读 switch 自守 → 又拒了
fallback 日志打了，采集却为空
After — 决策一个点，collect 收参数
interceptor：唯一决策点（含 fallback）
collect(request, decision)：行为完全由入参定

Problem. 「是否采集请求参数」在 interceptor 和 collector 里各读一次 switch；profiling fallback 只在两 switch 全 false 时触发，可 collector 内部重读同样的 false 又拒了——日志「by profiling fallback」后什么都不采。hutool 侧结构完全一致。

Solution. collect() 收显式 decision/context 入参而非内部重读 CollectionSwitch，唯一决策点放到 interceptor，让 fallback 真正表达「无视 switch 采集」。

  • locality：决策与效果一处
  • 死代码变活
  • fallback 路径可测
