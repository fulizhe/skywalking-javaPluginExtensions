After · 各自一把锁

SegmentRepository

water-level GC · payload 桥 · 写路径

MetricsRepository

分钟/小时表 · 6 个 SQL 读口 · 自己的游标与锁 lock B

AuditRepository

Problem

三张互不相关的表挤在同一个 synchronized(this)（16 处）上——servlet 线程的指标查询与 H2Shadow-Writer 的 segment 写共用一把锁，一次慢查询就让写入停顿。

Solution

metrics repository（分钟+小时表）与 audit repository 各自成为 module，拥有自己的 SQL、ResultSet 与锁；storage 只保留 segment 写路径与 payload 桥。

Wins

  • locality：读口不再阻塞写线程
  • interface 收窄到各 repository 那一组 SQL
  • metrics repository 可脱离写路径单测
  • H2 Web Console 从存储 module 里挪走
与 ADR-04 / ADR-05（H2 mem 为终态）不冲突：只动锁粒度与 module 边界，不改存储形态。

Strong in-process

Before · 三处各算一遍，两种去重键

来源：H2 结果行自身

去重键 bucket

去重键 bucket

来源：distinctMetricBuckets("minute",…)

三处必须一致，否则读数重复或漏桶

After · 一个 module 回答一次

逐桶读 · 聚合读 · rollup 前并入

LiveWindow module

H2 已落库桶集合 × 内存分钟行 → rowsNotYetPersisted(from, to)

独占"H2 已落库就以 H2 为准"的语义

Problem

"该分钟桶已落库就以 H2 为准，否则补内存行"写在三处，且两处按 bucket、一处按 endpoint@bucket 去重。三份一起漂移就是重复计数或漏桶——正是指标口径最容易出错处，注释里已互相引用提醒。

Solution

一个 module 独占"已落库桶 × 内存分钟行"的并集语义，暴露一个读口；逐桶读、聚合读、rollup 前并入三处都调它。

Wins

  • locality：口径一处，漂移不可能
  • 读口与 rollup 天然同口径
  • 可单测：喂内存行 + 假已落库桶集合
  • 去掉三份里两份重复的判定
