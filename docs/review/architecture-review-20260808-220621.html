Problem. One concept — "a rule is a parsed config string that matches an operation/url and carries a payload" — is spread across 18 small files in the alert package. The matcher plumbing is three shallow hops, each adding exactly one line of logic: PatternMatcherFactory only does new AntTracePatternMatcher(...), AntTracePatternMatcher only does AntPatternCache.get(...). Understanding the whole concept means reading all 18; the logic itself is ~600 lines.

Solution. Deepen RulesEngine into the module that owns parse + compile + match + bindings. Callers cross one interface: RulesEngine.fromConfig(...), then matchSlow / matchErrorIgnoreRuleIndex. The factory/cache/fast-path chain becomes implementation detail.

  • • locality — rule semantics live in one module, bugs concentrate
  • • leverage — one interface, N match call sites
  • • Delete 3 shallow pass-throughs (deletion test: complexity just moves, never concentrates)
  • • Newcomer reads 1 file instead of 18

One bounded LocalStore module behind every sender

Strong in-process

Files

toolkit/CircularBlockingQueue · override/JVMMetricsLocalSender · MeterLocalSender · LogReportServiceLocalClient · ProfileSnapshotLocalSender · reporter/logfile/LogFileTraceSegmentServiceClient

Before — 5 divergent stores

JVM → CircularBlockingQueue <Map> (cap 1000)
Meter → CircularBlockingQueue <MeterDataSnapshot> (cap 300)
Log → CircularBlockingQueue <Map> (cap 1000)
Profile → CircularBlockingQueue <Map> (cap 500)
Trace → synchronized LinkedHashMap, accessOrder=false
README calls it "LRU" — it's FIFO

After — one deep store

LocalStore <T>
add(T) · snapshot() · size()
eviction policy · boundedness · snapshot copy · locking — one place
JVM adapter (cap 1000)
Meter adapter (cap 300)
Log / Profile / Trace adapters

Problem. The "bounded cache that evicts oldest and serves a defensive snapshot" shape is re-implemented five times with divergent containers and semantics. The ring queue implements the entire BlockingQueue interface (201 lines) for one behavior, with its lock guarding only insert while reads (drainTo, iterator) skip it. The trace store claims LRU but is FIFO. Eviction, boundedness, threading, and snapshot-copy live in five places.

Solution. One deep LocalStore<T> module: interface add / snapshot / size. Implementation absorbs the eviction policy, capacity, snapshot copy, and locking. Each sender becomes a thin adapter that declares its capacity. The ring queue's public surface shrinks to three methods.

  • • locality — boundedness/threading/eviction verified once, not five times
  • • leverage — 5 call sites, one interface to learn and test
  • • FIFO-vs-LRU lie settled in one place
  • • Concurrent snapshot() guarded behind the seam

Problem. The agent-classloader ↔ plugin-classloader seam is crossed by cn.hutool string reflection (getLogfileStatMap, toggleEnable, snapshotQueue). Renaming a method silently breaks the plugin at runtime, and the interceptor itself warns "不要尝试进行类型转换". Two classloaders means two real adapters — the seam is real, but it's untyped.

Solution. A compiled contract module both sides satisfy: the interceptor calls one method (snapshot()) on a BootService-registered LocalStatusSnapshot; the six senders' getters become its implementation. Reflection collapses to one well-named call.

Constraint: SkyWalking's classloader model caps what crosses the seam — the contract must live in the agent-core classloader. Not an interface-design task yet; the seam placement is the decision to grill.

  • • leverage — one interface across both loaders
  • • locality — status assembly lives in one module
  • • Rename failures become compile errors, not silent gaps

Move thread lifecycle out of the dispatcher constructor

Worth exploring mock

Files

alert/AsyncTraceAlertDispatcher

Before

constructor → new Thread(this).start()
no test: constructing starts a live thread
resolveDispatchQueueSize() hard-codes 512, config read commented out

After

DispatchPipeline — evaluate + dedup + offer, constructed without threads
thin boot-owner starts the consumer; tests drive the pipeline

Problem. afterTraceMerged(traceId, mergedMap) is actually a deep interface — evaluate, dedup, queue, metrics in one call. But the constructor spawns a daemon thread and hard-codes the queue size with the config read commented out (AsyncTraceAlertDispatcher.java:174-177). The module is untestable through its interface because constructing it starts live infrastructure.

Solution. Split construction from lifecycle: a pure pipeline module (evaluator + notified-flags + bounded queue) testable through afterTraceMerged, and a thin owner that starts/stops the consumer thread.

  • • the interface is the test surface — drive pipeline without threads
  • • Config read restored, not commented out
  • • locality — dispatch logic concentrates, lifecycle stays thin

Top recommendation

Collapse the rule chain into one deep RulesEngine. It hits the package this repo is actively changing (the alert hot spot in recent commits) and the deletion test is unambiguous — the factory and matcher hops are pure pass-throughs whose complexity would just move. The other three candidates are real but land elsewhere: B is foundational and worth doing next, C and D are seam-placement questions that belong in a grilling session.
